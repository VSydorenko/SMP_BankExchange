# Інструмент зразків виписок

Відтворюваний ланцюжок «сирий файл виписки → знеособлений зразок + еталон очікуваних операцій». Результат
знеособлення перевіряється автоматично (D22 а/б/в), без перегляду людиною. Інструмент лежить поза
воркспейсом Уніки (автоскан Уніки падає на першому не-UTF-8 файлі, а зразки — у windows-1251); у воркспейс
потрапляють лише готові двійкові макети тестового розширення.

**Сирих даних тут немає й бути не може.** Сирі зразки, їхні робочі копії, мапа «реальне → вигадане» і
знеособлені файли до коміту лежать лише в гітігнорованій `temp/`. У `config.json` — маски шляхів і
службові списки, без жодного реального значення (теку клієнта описано маскою `* - Виписки банка`).

## Запуск

Python 3, **з прапорцем `-P`** (не `-I`: `-I` вимикає користувацький site-packages, де стоїть
`python-stdnum`, потрібний валідаторам). Запускати з теки поза сирими даними.

```
python -P tools/statement-samples/samples.py <команда> ...
```

| Команда | Що робить | Код виходу |
|---|---|---|
| `selfcheck --raw R` | оракул на сирих: кількості, розкладки старих обробок проти розбору «за назвою», звірки ОТП, масштаб `SUMMA`, баланс УкрГазу | 1 при розбіжності з очікуваним |
| `anonymize --raw R --out O` | знеособлює всі зразки з `config.json`, пише `O/<id>.bin` і `O/map.json` (мапа одна на прогін) | 0 |
| `check-a/-b/-c --raw R --out O [--control] [--json F]` | перевірка D22 (а), (б) або (в); для (в) ще й звірка пар форматів | 1 при порушенні |
| `verify --raw R --out O [--json F]` | контроль (а) на сирому + а/б/в на знеособленому + пари | 1 при порушенні |
| `etalons --raw R --out O` | пише `O/<id>.etalon.txt` (формат нижче) зі знеособленого файлу | 0 |
| `epf-list --epf-src epf/src [--exclude Сбербанк] [--out F]` | перелік обробок `epf/src` для матриці формат × зразок (задача 11) | 0 |
| `guard --raw R [--files ...] [--staged]` | сторож перед комітом: лексеми мапи у файлах | 1 при збігах; 2, якщо контроль не падає |

Тести самого інструменту (синтетичні дані): `python -P -m unittest discover -s tests` з цієї теки.

## Оракул: два режими

Оракул — Python-розбір кожного формату двома незалежними лініями:

* **«за розкладкою»** (`sslib/legacy.py`) — емуляція `ЗаполнитьСтроку` нинішніх обробок `epf/src` (колонки за
  номерами, правила напряму, дати, суми). Це не запуск 1С; прийняті припущення про платформу — у
  `PLATFORM_ASSUMPTIONS`;
* **«за назвою»** (`sslib/named.py`) — читачі, що знаходять поле за назвою колонки / поля / атрибута. Збіг двох ліній
  доводить, що розкладка читає саме назване поле.

DBF читається двома моделями, і кожен виклик `util.read_dbf` називає модель (`model=`, значення за
замовчуванням немає): `product` — контейнер `ЗаписиDBF` продукту (NUL → апостроф, справа знімаються лише пробіли,
вилучені пропускаються, номер запису фізичний); `legacy` — XBase старих обробок (значення обрізається на першому
NUL, вилучені пропускаються, номера для людини немає). «За назвою» (`named.py`) представляє продукт, «за
розкладкою» (`legacy.py`) — стару обробку; їх не зіставляти за номером запису.

Режими виходу «за розкладкою»:

* `old` — «стара обробка»: емуляція як є, з усіма особливостями й дефектами;
* `expected` — «очікуване»: стара обробка плюс рівно п'ять відступів плану 03. Кожен відступ — окрема іменована
  функція: `dev1_split_quoted` (лапки в CSV), `dev2_amount` / `dev2_date` / `dev2_currency` /
  `dev2_sens_fop_currency` (нерозібране значення — помилка, не 0; буквений код валюти — числовий; «валюта»
  Сенсу-ФОП — порожня), `dev3_foreign_accounts` (чужі рахунки — у діагностику), `dev4_reader_encoding`
  (кодування заявляє читач), `dev5_oschad_no_temp_file` (DBF читається з пам'яті). Інші відступи, навіть
  очевидні покращення, — питання планувальнику.

Еталон макета рахується в режимі `expected`.

## Знеособлення

Кожне поле кожного формату мусить мати роль (`sslib/schema.py`): `KEEP` (сума, дата, час, валюта, напрям, номер
документа, МФО, коди операцій), `CODE`, `ACC`, `NAME`, `BANKNAME`, `PURPOSE`, `SCRAMBLE`, `DOCTYPE`. Невідома
колонка / поле / атрибут — помилка, а не мовчазне збереження.

* Заміна випадкова (`SystemRandom`); хеші без секрету не використовуються. Мапа одна на прогін і спільна для всіх
  файлів: той самий контрагент чи рахунок отримує ту саму заміну в CSV, DBF і XML, тож звірка форматів
  переживає знеособлення.
* Коди: ЄДРПОУ (8 цифр) і ІПН (10 цифр) — з правильною контрольною сумою; IBAN — mod 97, код банку (МФО)
  зберігається; зв'язок «IBAN ↔ старий номер рахунку» зберігається (одне ядро номера). Довжини збережено.
* Назви: слова замінюються вигаданими тієї ж довжини й регістру; юридичні форми зі списку `allowed_words` лишаються.
* Призначення: фраза зі словника за категорією (комісія, податок, зарплата, відсотки, послуги, товар, інше), яку
  визначає ключове слово сирого тексту. Зберігаються кількість `;`, лапок, керівних символів (NUL, переноси) і
  службових цифр. Шаблонних текстів банку дослівно не лишається (`verbatim_texts` порожній; додавати лише з
  погодженням планувальника).
* Фіксована ширина й DBF: довжина поля — частина структури; вирівнювання (лівосторонє / правостороннє) і байт
  доповнення зберігаються. Байти поза відомими зрізами (проміжки) перемішуються, якщо не порожні й не нулі.
* XLS: підміна на місці в таблиці спільних рядків із тією ж кількістю символів і тим самим кодуванням; числові
  комірки чутливих ролей підміняються як `double`.

## Перевірки D22

* **(а)** жодне чутливе значення сирого файлу не трапляється в знеособленому. Лексикон — усі числа від 5 цифр і
  слова з великої літери (від 3 літер) чутливих полів + повні значення (назви, призначення, коди, рахунки від 6
  символів). Пошук — по всіх байтах знеособленого файлу в трьох поданнях (windows-1251 і UTF-16LE з обома
  вирівнюваннями); для DBF / фіксованої ширини / XLS числа шукаються в межах поля. Із лексикону явно виключаються
  й рахуються: лексеми збережених полів («поля оракула»: сума, дата, номер документа тощо), слова структури
  (заголовки, імена полів / тегів / атрибутів) і `allowed_words`. Залишок поза полями (скелет файлу) мусить
  складатися зі слів структури. **Додатково — шаблонний пошук:** кожен IBAN-подібний рядок і кожне 8/10-цифрове
  число знеособленого мусить бути виданим значенням (є в мапі) або лежати у збереженому полі (дата, сума, номер).
  **Контроль** (`--control`): та сама перевірка на сирому файлі мусить давати збіги.
* **(б)** структура та сама: скелет файлу (усе, крім значень полів) збігається байт у байт; кінці рядків, NUL, BOM,
  кодування; для CSV — кількість рядків і колонок і лапки по кожному полю; для фіксованої ширини й DBF — довжина
  файлу, рядка й поля. У значень: збережені довжини кодів і рахунків, кількість `;` `"` NUL і переносів у назвах
  і призначеннях, контрольні суми (`python-stdnum`: `stdnum.iban`, `stdnum.ua.edrpou`, `stdnum.ua.rntrc`),
  код банку в IBAN.
* **(в)** розбір оракулом (обома лініями) сирого і знеособленого дає однакові значення в усіх полях, крім
  замінених; замінені дорівнюють значенню з мапи. Для пар «та сама виписка у двох форматах» (ОТП `.dat` ↔ `.dbf`,
  `.dbf` ↔ `.xml`) знеособлені версії звіряються між собою так само, як сирі (ті самі кількості збігів по полях).

Скорочені зразки (`take_rows` у конфігурації) порівнюються з сирим файлом, скороченим так само.

## Сторож перед комітом

`guard` бере з усіх сирих зразків числа від 5 цифр і власні назви (поля `NAME` / `BANKNAME`, довжина від 4; слова,
які трапляються також з малої літери, і слова з `allowed_words` / `guard_allowed_words` не беруться) та шукає їх у
файлах (`--files` або `--staged`; імена файлів теж). Нуль збігів — умова точки коміту. Перед роботою сторож
підмішує до нейтрального тексту кілька сирих лексем і вимагає, щоб вони знайшлися (інакше код 2): пошук, який не
вміє падати, нічого не доводить. Сторож призначено для коду, конфігурації, документації й журналу; знеособлені
макети й еталони охороняє перевірка (а) (на випадкових цифрах п'ятицифрові збіги з сирими неминучі).

## Формат еталона `СМП_ТестЭталон<…>` (версія 1)

Текст UTF-8, рядки через LF. Значення екрановані: `\` → `\\`, TAB → `\t`, LF → `\n`, CR → `\r`, тож один
запис — один фізичний рядок; поля запису розділені символом TAB. Рядки, що починаються з `#`, — коментар.

```
# СМП_ТестЭталон
# Версия формата: 1
# Режим: ожидаемое (старая обработка + отступы 1-5)
[Образец]
Идентификатор=<суфікс макета>
Контейнер=csv|lines|dbf|xml|xls
Принимается=Да|Нет
```

Для `Принимается=Нет` (зразок мусить бути відхилений форматом) далі лише `Причина=` (категорія, не значення) і
`ЗаписейИсточника=` (скільки записів розбирає оракул «за назвою»); операцій нема.

Для `Принимается=Да` далі:

```
Схема=<розкладка оракула>
ЗаписейИсточника=<записів у джерелі, без заголовка>
ПропущенныхСтрок=<рядки, які стара обробка пропускає: порожній код у першій колонці>
[Счета]                         власні рахунки у порядку першої появи: НомерСчета TAB кількість операцій
НомерСчетаЧтения=<перший з [Счета]; він же Параметры.НомерСчета у тесті>
[Операции]                      перший рядок — назви колонок:
  ПорядковыйНомер  НомерСчета  Валюта  ДатаОперации  НомерДокумента  Сумма  Направление
  КонтрагентНаименование  КонтрагентНомерСчета  КонтрагентКод  КонтрагентМФО  НазначениеПлатежа
[Диагностика]                   перший рядок — Уровень TAB ПорядковыйНомер TAB Что TAB СырьеЗначение
[ЧужиеСчета]                    перший рядок — НомерСчета TAB НомераСтрок: рядки, чий власний рахунок ≠ НомерСчетаЧтения
```

* `ПорядковыйНомер` — номер у джерелі з одиниці: фізичний рядок файлу (заголовок CSV — рядок 1), запис DBF, елемент
  XML.
* `Валюта` — три цифри або порожньо (= валюта рахунку); `ДатаОперации` — `ГГГГ-ММ-ДДTгг:хх:сс`; `Сумма` — десяткове
  число з крапкою й двома знаками; `Направление` — `Поступило` / `Списано`.
* Колонок `ДатаДокумента` і `ИдентификаторОперации` в еталоні немає: стара обробка їх не читає, тест їх не звіряє.
* `[Диагностика]`: `Что` — `amount` / `date` / `currency` (відступ 2), `СырьеЗначение` — сире значення з файлу.
  На реальних зразках очікувана діагностика порожня.
* `[ЧужиеСчета]` — лише інформація про відступ 3; рівень повідомлення й текст визначає задача 5.

Тест 1С читає макет еталона, розбирає секції й порівнює з тим, що повернув читач на макеті `СМП_ТестВыписка<…>` (або
на тому ж файлі через реєстр). Еталон рахується з **знеособленого** файлу оракулом, а не BSL-кодом, який він
перевіряє.

## Макети тестового розширення

Макети лежать у тестовому розширенні `SMP_BankExchange_SMB_Tests` у власній обробці `DataProcessor.СМП_ТестыМакеты`
(шаблон потребує власника; сама обробка нічого не робить). Тести задач 6–11 дістають макет за ідентифікатором зразка `Ид`
(колонка «Ид» нижче) **лише так**, без власного коду пошуку:

```bsl
Данные = Обработки.СМП_ТестыМакеты.ПолучитьМакет("СМП_ТестВыписка" + Ид);   // ДвоичныеДанные: знеособлений файл
Эталон = Обработки.СМП_ТестыМакеты.ПолучитьМакет("СМП_ТестЭталон" + Ид);    // ТекстовыйДокумент: еталон v1
```

* `СМП_ТестВыписка<Ид>` — макет типу «двоичные данные»: байти файлу без змін (windows-1251 для текстових форматів;
  NUL і кінці рядків збережено). Передавати читачеві як є.
* `СМП_ТестЭталон<Ид>` — текстовий макет (`ТекстовыйДокумент`; у файлі `Template.txt` — UTF-8 з BOM). Читати рядками
  (`Эталон.ПолучитьСтроку(Н)`), розбирати за форматом v1 вище: секції `[Образец]`, `[Счета]`, `[Операции]`, `[Диагностика]`,
  `[ЧужиеСчета]`; поля запису розділені TAB; значення екрановані (`\` → `\\`, TAB → `\t`, LF → `\n`, CR → `\r`). Еталон зразка, який мусить бути
  відхилений, містить лише `[Образец]` з `Принимается=Нет`.
* `СМП_ТестПереченьОбработок` — текстовий макет: імена обробок `epf/src` без Сбербанку, по одному в рядку (для матриці
  «перевірка формату × зразок» задачі 11). Перегенерація: `epf-list --epf-src epf/src --out <файл>`.
  **Перегенеровувати при кожній зміні складу `epf/src`**: тест повноти реєстру не бачить диска й порівнює реєстр лише з
  макетом, тож застарілий макет робить перевірку помилково зеленою.

### Скан зібраних `.epf` на витік

Тестові `.epf`, що збираються з вихідників `tests/epf-src` тестового розширення, — ще одне місце, куди сирі дані
можуть потрапити (контейнер `.epf` стискає вміст, і пошук по сирих байтах файлу стиснутого вмісту не бачить). Тому скан:

* шукає лексеми сторожа не лише в байтах файлу, а й у **розпакованих deflate-потоках** контейнера;
* мусить мати контроль усередині стиснутого потоку: у зібрану для контролю обробку вкладається відома лексема, і скан
  зобов'язаний її знайти (пошук, який не вміє падати, нічого не доводить);
* повторюється після кожної зміни `tests/epf-src`: контейнер недетермінований (повторна збірка дає інші байти), тож
  результат попередньої збірки нічого не каже про нову.

Ідентифікатори (`config.json`, поле `id`; «Прийнятий» — формат читається, «Відхилюваний» — читач мусить відхилити файл):

| `CSVАваль` | прийнятий | iFOBS CSV, Аваль; колонка номера документа зветься «Документ» |
| `CSVВосток` | прийнятий | iFOBS CSV, Восток; кінцевий `;` |
| `CSVУниверсалNUL` | прийнятий | iFOBS CSV, Універсал; NUL у призначенні, кінцевий `;` |
| `CSVПроКредит` | прийнятий | iFOBS CSV, ПроКредит |
| `CSVУкрСиб` | прийнятий | iFOBS CSV, УкрСиб; усі поля в лапках, `;` усередині призначення |
| `CSVУкрГаз` | прийнятий | CSV УкрГаз; залишки |
| `CSVСенсТОВ` | прийнятий | CSV Сенс, гілка ТОВ |

| `DBFОТП` | відхилюваний | ОТП у DBF (пара до `DATОТП1191`) |
| `DBFОТПДоба` | відхилюваний | ОТП у DBF, одна доба (пара до `XMLОТПДоба`) |
| `XMLОТПДоба` | відхилюваний | ОТП у XML, одна доба |

Відповідність джерелам перевіряє сам інструмент (`config.json`); при розходженні цього переліку з конфігурацією правдою є конфігурація.

**Повторно не знеособлювати.** Мапа «реальне → вигадане» живе лише в `temp/anon/map.json` (гітігноровано) і одна на прогін. Повторний
запуск `anonymize` генерує інші вигадані значення, тож закомічені макети й еталони перестали б відповідати мапі та
перевіркам (в). Макети, що вже лежать у розширенні, змінюються лише свідомо, разом з еталонами, і лише з наявного прогону та
його мапи; не запускайте `anonymize` у ту саму теку, поки макети не потрібно замінити.

## Відомі межі

* Емуляція старих обробок — не запуск 1С; припущення про платформу (`legacy.PLATFORM_ASSUMPTIONS`) не перевірені тут.
* Імена в `[Операции]` для ОТП `.dat` беруться за розкладкою старої обробки, яка читає ім'я зі зсувом від межі поля
  (відомий дефект); у перевірці (в) такі імена порівнюються за довжиною.
* Зразки з API-банків (ПУМБ тощо) не оброблюються; файли `settings*` не відкриваються ніколи.
