# Формат запису відповідей API (рекордер)

Версії формату: **1** і **2**. Формат фіксує рекордер (задача 1 плану 05а); його ж використовують знеособлювач
(задача 2) і транспорт відтворення в 1С (задача 3). Зміна формату — нова версія в полі `formatVersion`,
а не мовчазна правка полів. Читачі приймають обидві версії; поля, яких версія не знає, ігноруються. Запис пишеться
у версії 2 лише тоді, коли користується чимось із розділу «Версія 2» (метод `POST`, `request.port`, тіло запиту);
інакше він лишається версією 1 байт у байт. Версія обміну не вища за версію маніфесту, версія маніфесту — найвища з версій
обмінів.

## Версія 2 (план 05б-2, задача 1a)

Лише поле `request` обміну, відповідь і маніфест — як у версії 1.

* `method` — `GET` або `POST`.
* `port` — ціле `1…65535`, необов'язкове (відсутнє — стандартний порт схеми). Відтворення порівнює хост **разом із портом**.
* Тіло запиту — **рівно одна** з форм (для `POST` обов'язкова, для `GET` не потрібна):
  * `bodyBase64` + `bodyLength` — байти як пішли;
  * `bodyMasked` = `{ "text": "<JSON>", "fields": ["a.b", …] }` — JSON-тіло, у якому кожне поле з переліку (крапка — вкладений
    ключ) має значення-маркер `"<masked>"`; інших маркерів у тексті немає, перелік не порожній;
  * `bodyOmitted: true` + непорожнє `bodyOmittedReason` — тіло в запис не потрапляє (автентифікація: пароль, секрет).
* Заголовків запиту й тут немає.

Звіряння відтворенням: метод, хост з портом, шлях, `query` — як раніше. Тіло: `bodyBase64`, JSON — за розібраним
значенням (порядок ключів і пробіли неістотні; значення, тип значення й склад ключів істотні), не JSON — за байтами;
`bodyMasked` — як JSON, а поле-маркер лише має бути присутнє (значення будь-яке); `bodyOmitted` — тіло не звіряється, лише метод
і шлях. Текст розбіжності значень тіла не повторює.

## ПУМБ у рекордері (план 05б-2, задача 1)

Банк `pumb`, дві адреси: токен — `auth.fuib.com` (стандартний порт, `port` у запису немає), читання — `service.fuib.com`, порт `4103` (`request.port = 4103`
у кожному обміні, бо відтворення порівнює хост разом із портом). Рекордер пише в формат версії 2 за тим самим правилом, що й `apilib/recording.py`
(`_uses_v2`): версія 2 — якщо запит має метод не `GET`, або `port`, або будь-яку форму тіла запиту; запис без жодного з цього лишається версією 1.

* **Автентифікація** (`POST …/openid-connect/token`): `bodyOmitted: true` + `bodyOmittedReason` (пароль і секрет клієнта в запис не потрапляють).
  Відповідь записується **замаскованою**: кожне рядкове значення, крім `token_type`, `scope`, `error`, `error_description`, `error_uri`, замінено маркером тієї ж
  довжини й форми (літера → `a`/`A`, цифра → `9`, решта символів лишається); числа й булеві не змінюються. Відповідь, що не є JSON-об'єктом, маскується цілком таким самим способом.
* **Читання** (`GET /account`, `POST /document/searcher`, `POST /document/period-transactions`): тіло запиту — `bodyBase64` + `bodyLength`, як пішло.
  Форма `bodyMasked` рекордером ПУМБ не використовується (поля тіла не секретні).
* Платіжні й змінювальні методи в білий список не входять і додатково відхиляються за назвою (`order`, `delete`, `sign`, …).

## Що це

Запис прогону — тека `<корінь записів>/<банк>/<мітка прогону>/`:

| Файл | Що |
|---|---|
| `recording.json` | Маніфест: версія формату, банк, мітка, час, стан прогону, **упорядкований** перелік обмінів. |
| `0001.json`, `0002.json`, … | Один обмін (запит → відповідь) на файл; номер — порядок у прогоні. |
| `summary-agent.txt` | Зведення лише з кількостями (для агента). Не є частиною формату обміну. |
| `LEAK-DETECTED.txt` | З'являється лише якщо самоперевірка знайшла токен. Тоді теку нікому не передають. |

Суми й ідентифікатори для звірки з кабінетом лежать **поза текою записів** (її читає агент): `owner-only/<банк>/<мітка>/reconcile.txt` поряд із конфігурацією.

Стани прогону (`state` у маніфесті): `ok`; `incomplete` (збій рекордера в сценарії); `aborted` (банк повідомив,
що йде регламент); `error`; `interrupted` (прогін перервано); `leak-detected`.

## Маніфест `recording.json`

```
{
  "format": "smp-api-recording", "formatVersion": 1, "recorderVersion": "...",
  "bank": "privat" | "mono-corp" | "mono-fop" | "pumb", "runLabel": "...",
  "startedUtc": "...", "finishedUtc": "...", "state": "ok", "note": "",
  "exchanges": [ { "seq": 1, "file": "0001.json", "scenario": "...", "status": 200, "failure": null }, ... ]
}
```

`exchanges` — єдине джерело порядку. `status` — HTTP-статус або `null`, якщо був збій мережі (тоді `failure` — вид збою).

## Обмін `NNNN.json`

```
{
  "format": "smp-api-exchange", "formatVersion": 1,
  "seq": 1, "scenario": "privat_a1_tx_work_limit",
  "startedUtc": "2026-10-15T18:53:23.575Z", "durationMs": 12,
  "request":  { "method": "GET", "host": "acp.privatbank.ua", "path": "/api/statements/transactions", "query": "acc=...&startDate=..." },
  "response": { "status": 200, "headers": [ ["content-type", "application/json;charset=utf-8"] ],
                "bodyLength": 128, "bodyBase64": "..." },
  "failure":  null
}
```

* **`request`** — метод (у версії 1 завжди `GET`; версія 2 — вище), хост, шлях і **рядок запиту як він пішов** (`query`, без `?`, у тому порядку й
  кодуванні, що були надіслані; може бути порожнім). Заголовків запиту в записі **немає взагалі**: токен лежить
  у заголовках, а структура запису для них місця не має (функція запису їх не приймає). Токен у адресі не передається
  жодним із трьох API.
* **`response.status`** — HTTP-статус числом.
* **`response.headers`** — масив пар `[ім'я малими літерами, значення]`. Лише **білий список**: `content-type`,
  `retry-after`, `date`, заголовки лімітів (`x-rate-limit-*`, `x-ratelimit-*`, `ratelimit-*`). Решта (куки, ехо,
  службові) відкидається, навіть якщо банк їх повернув.
* **`response.bodyBase64`** — тіло відповіді **байтами, як прийшли**, у Base64 (стандартна абетка з `=`).
  `bodyLength` — довжина в байтах до кодування (контроль цілісності). Тіло зберігається **розпакованим**: транспортне
  стиснення (gzip/deflate/br) клієнт знімає до запису, тож `content-encoding` у записі немає, а байти — вміст відповіді.
  Кодування тіла (UTF-8, cp1251 — ПриватБанк може відповідати в cp1251) — частина даних; його визначає
  `content-type` (`charset=`) і, за його відсутності, сам вміст. Рекордер тіло **не перекодовує й не форматує**.
* **`failure`** — `null`, якщо відповідь отримано. Якщо мережа підвела: `{ "kind": "timeout" | "network" | "other" (або stuck_cursor | no_candidate — див. нижче),
  "text": "..." }`, тоді `response` дорівнює `null`. Текст збою не містить заголовків запиту, а значення токенів у ньому
  замасковано (`<мітка секрету>`).

Обмін або має `response`, або `failure`; обох одночасно не буває.

`429`, `401`, `400`, `404` тощо — звичайні відповіді з `status`; їх записують так само, як `200`. Рекордер
повторює запит після `429` не більше одного разу, і обидві спроби лежать у записі окремими обмінами. Виняток —
сценарій `fop_client_info_then_statement_immediately` (вимір D36 п. 9): там запит виписки один, без повтору, і
`429` лишається єдиним обміном з цим статусом.

## Чому JSON з Base64, а не сирі файли чи HAR

1. **Тіло байтами.** Приватбанк може віддати cp1251; JSON-рядок або HAR-поле `text` перекодували б тіло. Base64 зберігає
   байти як є, тож кодування лишається частиною структури (антипатерн задачі 1: тіло перекодованим рядком).
2. **1С читає це без зусиль.** `ЧтениеJSON` розбирає обмін, а `Base64Значение(...)` повертає `ДвоичныеДанные`
   тіла. Знеособлений запис ляже в макет типу `ДвоичныеДанные` так само, як зразки файлових читачів; транспорт відтворення
   віддасть читачу ті самі байти, що дав би справжній HTTP.
3. **Один обмін — один файл.** Тест кличе конектор на одному сценарії, тож перелік `exchanges` дає потрібні файли за
   `scenario`, і не доводиться вантажити весь прогін.
4. **Порядок явний.** Відтворення йде за `seq`, а не за іменами файлів чи часом зміни.
5. **Видно, що саме збережено.** Відсутність поля `headers` запиту очевидна в самій схемі; інвентар полів малий, і білий
   список заголовків відповіді читається в одному місці коду (`Select-AllowedHeaders`).

HAR відкинуто: він несе заголовки запиту (отже, токени), час сервера, куки й багато зайвого, а його тіло — рядок.

## Що від формату потрібно споживачам

**Знеособлювач (задача 2).** Розкодовує `bodyBase64` у байти, знеособлює за кодуванням тіла, кодує назад і перераховує
`bodyLength`. Знеособлює також `request.path` і `request.query` (там IBAN і ідентифікатор рахунку monobank ФОП).
Не змінює `seq`, `scenario`, `status`, `headers`, `failure.kind`. Перевірки а/б/в (D22) — по розкодованих тілах і в усіх
кодуваннях, зокрема по розкодованих `\uXXXX`.

**Транспорт відтворення (задача 3).** Віддає відповіді за порядком `exchanges`; для перевірки зіставляє `method`, `path`
і `query` запиту конектора з записаними (з урахуванням, що знеособлення міняє значення рахунків, а не структуру). Збій
мережі відтворює як відповідь з ознакою збою (D36 п. 1), без заголовків запиту в тексті.

## Сценарії і їхні імена

Поле `scenario` — стабільний ідентифікатор сценарію рекордера (`privat_a1_tx_work_limit`, `corp_a1_daily_windows`,
`fop_client_info_then_statement_immediately`, `*_errors_*` тощо). Частина `aN` — номер рахунку з конфігурації. Перелік
і сенс кожного — у `README.md`.

### Сценарії run3: межі запиту й насичені періоди

* `corp_aN_statement_small_limit_overlap` — як `_statement_small_limit`, але наступний запит іде з `to` = найраніша `time`
  сторінки + 1 (D36 п. 11); лише юросіб (у ФОП немає `limit`).
* `corp_aN_statement_saturated_limit500` — насичений період юросіб (`SaturatedPeriod`, `limit=500`), продовження з `to` = найраніша `time`
  сторінки + 1, збіг запитів — `stuck_cursor`.
* `privat_aN_datkl_boundary` — ПриватБанк: запит транзакцій за один день `DAT_OD` (`startDate` = `endDate`) операції, обраної рекордером серед
  прочитаних `privat_aN_tx_work_limit` (або `privat_aN_datkl_source`, якщо його не було): день `DAT_KL` ≠ день `DAT_OD`, з кількох — найдалі від
  меж періоду. Параметри `acc`, `limit` — як у `tx_work_limit`, усі сторінки за `exist_next_page`. Немає кандидата — `no_candidate`, запиту немає.
* `fop_a1_saturated` — насичений період ФОП (`SaturatedPeriod`) до сторінки, коротшої за 500, продовження так само, з паузою 61 с.
  Без `SaturatedPeriod` у записі лише порожній сценарій у `summary-agent.txt` (обмінів немає).
* Пари меж, `{corp_aN|fop_a1}_boundary_{from|to}_{eq|shift}`: `from_eq` — `from` = t; `from_shift` — `from` = t − 1 (обидва зі спільним
  `to` = менше з t + 3600 і кінця періоду); `to_eq` — `to` = t; `to_shift` — `to` = t + 1 (обидва зі спільним `from` = більше з t − 3600
  і початку періоду). t — `time` операції, обраної рекордером: єдина у своїй секунді серед усіх прочитаних сторінок вибірки
  й лише зі сторінки, НЕ повної за її `limit` (юросіб — коротшої за `limit` запиту, ФОП — коротшої за 500). Значення t у
  записі немає окремим полем — воно видно з `query`/`path` обмінів (`from_eq`, `to_eq`). Вибірка — відповідь звичайного сценарію
  виписки цього ж прогону за основний період (юросіб — `statement_limit500`, ФОП — `statement_segment_NN`); якщо його немає,
  рекордер робить один запит у сценарії `{corp_aN|fop_a1}_boundary_source` (юросіб: `limit=500` за період; ФОП: перша сторінка
  першого відрізка). Висновку про включність рекордер не робить.

### Збої на боці рекордера (`failure.kind`)

Крім `timeout | network | other` (збій HTTP-запиту) є два види, коли **запит не надсилався**: обмін має `response: null`, а
`failure.text` пояснює причину. Відтворення трактує їх не як відповідь банку, а як позначку «рекордер зупинився тут».

| `failure.kind` | Коли | Що в `request` |
|---|---|---|
| `stuck_cursor` | Продовження з `to` = найраніша `time` + 1 збіглось би з попереднім запитом (повна сторінка в одній секунді). Читання сценарію зупинено. | запит, який повторився б (шлях і `query`) |
| `no_candidate` | monobank: для пар меж немає операції, єдиної у своїй секунді на неповній сторінці вибірки; пар не робили (сценарій `…_boundary_candidate`). ПриватБанк: немає операції з днем `DAT_KL` ≠ `DAT_OD`; запиту не робили (сценарій `privat_aN_datkl_boundary`). | запит вибірки за основний період |

## Інваріанти, які перевіряє самотест

* у жодному записаному файлі, у жодному кодуванні (UTF-8, UTF-16LE/BE, cp1251, cp866, Base64, URL-кодування,
  `\uXXXX`), не трапляється значення токена з конфігурації — ні в сирому файлі, ні в розкодованому `bodyBase64`;
* заголовки відповіді поза білим списком у запис не потрапляють, а текст збою позбавлений значень секретів;
* метод, хост, порт і шлях запиту входять до білого списку читання (`GET` для трьох перших банків; для ПУМБ — три `POST` і `GET /account`); платіжний метод ПУМБ відхиляється;
* у записі ПУМБ немає тіла запиту автентифікації, а відповідь автентифікації замаскована; значення, видані банком у прогоні, шукаються в усіх файлах запису, консольному журналі (`console.log`) і перенаправленому `stderr`.
