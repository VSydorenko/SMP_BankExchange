# Формат запису відповідей API (рекордер)

Версія формату: **1**. Формат фіксує рекордер (задача 1 плану 05а); його ж використовують знеособлювач
(задача 2) і транспорт відтворення в 1С (задача 3). Зміна формату — нова версія в полі `formatVersion`,
а не мовчазна правка полів.

## Що це

Запис прогону — тека `<корінь записів>/<банк>/<мітка прогону>/`:

| Файл | Що |
|---|---|
| `recording.json` | Маніфест: версія формату, банк, мітка, час, стан прогону, **упорядкований** перелік обмінів. |
| `0001.json`, `0002.json`, … | Один обмін (запит → відповідь) на файл; номер — порядок у прогоні. |
| `summary-agent.txt` | Зведення лише з кількостями (для агента). Не є частиною формату обміну. |
| `LEAK-DETECTED.txt` | З'являється лише якщо самоперевірка знайшла токен. Тоді теку нікому не передають. |

Суми й ідентифікатори для звірки з кабінетом лежать **поза текою записів** (її читає агент): `owner-only/<банк>/<мітка>/reconcile.txt` поряд із конфігурацією.

Стани прогону (`state` у маніфесті): `ok`; `incomplete` (збій рекордера в сценарії); `aborted` (банк повідомив,
що йде регламент); `error`; `interrupted` (прогін перервано); `leak-detected`.

## Маніфест `recording.json`

```
{
  "format": "smp-api-recording", "formatVersion": 1, "recorderVersion": "...",
  "bank": "privat" | "mono-corp" | "mono-fop", "runLabel": "...",
  "startedUtc": "...", "finishedUtc": "...", "state": "ok", "note": "",
  "exchanges": [ { "seq": 1, "file": "0001.json", "scenario": "...", "status": 200, "failure": null }, ... ]
}
```

`exchanges` — єдине джерело порядку. `status` — HTTP-статус або `null`, якщо був збій мережі (тоді `failure` — вид збою).

## Обмін `NNNN.json`

```
{
  "format": "smp-api-exchange", "formatVersion": 1,
  "seq": 1, "scenario": "privat_a1_tx_work_limit",
  "startedUtc": "2026-10-15T18:53:23.575Z", "durationMs": 12,
  "request":  { "method": "GET", "host": "acp.privatbank.ua", "path": "/api/statements/transactions", "query": "acc=...&startDate=..." },
  "response": { "status": 200, "headers": [ ["content-type", "application/json;charset=utf-8"] ],
                "bodyLength": 128, "bodyBase64": "..." },
  "failure":  null
}
```

* **`request`** — метод (завжди `GET`), хост, шлях і **рядок запиту як він пішов** (`query`, без `?`, у тому порядку й
  кодуванні, що були надіслані; може бути порожнім). Заголовків запиту в записі **немає взагалі**: токен лежить
  у заголовках, а структура запису для них місця не має (функція запису їх не приймає). Токен у адресі не передається
  жодним із трьох API.
* **`response.status`** — HTTP-статус числом.
* **`response.headers`** — масив пар `[ім'я малими літерами, значення]`. Лише **білий список**: `content-type`,
  `retry-after`, `date`, заголовки лімітів (`x-rate-limit-*`, `x-ratelimit-*`, `ratelimit-*`). Решта (куки, ехо,
  службові) відкидається, навіть якщо банк їх повернув.
* **`response.bodyBase64`** — тіло відповіді **байтами, як прийшли**, у Base64 (стандартна абетка з `=`).
  `bodyLength` — довжина в байтах до кодування (контроль цілісності). Тіло зберігається **розпакованим**: транспортне
  стиснення (gzip/deflate/br) клієнт знімає до запису, тож `content-encoding` у записі немає, а байти — вміст відповіді.
  Кодування тіла (UTF-8, cp1251 — ПриватБанк може відповідати в cp1251) — частина даних; його визначає
  `content-type` (`charset=`) і, за його відсутності, сам вміст. Рекордер тіло **не перекодовує й не форматує**.
* **`failure`** — `null`, якщо відповідь отримано. Якщо мережа підвела: `{ "kind": "timeout" | "network" | "other",
  "text": "..." }`, тоді `response` дорівнює `null`. Текст збою не містить заголовків запиту, а значення токенів у ньому
  замасковано (`<мітка секрету>`).

Обмін або має `response`, або `failure`; обох одночасно не буває.

`429`, `401`, `400`, `404` тощо — звичайні відповіді з `status`; їх записують так само, як `200`. Рекордер
повторює запит після `429` не більше одного разу, і обидві спроби лежать у записі окремими обмінами. Виняток —
сценарій `fop_client_info_then_statement_immediately` (вимір D36 п. 9): там запит виписки один, без повтору, і
`429` лишається єдиним обміном з цим статусом.

## Чому JSON з Base64, а не сирі файли чи HAR

1. **Тіло байтами.** Приватбанк може віддати cp1251; JSON-рядок або HAR-поле `text` перекодували б тіло. Base64 зберігає
   байти як є, тож кодування лишається частиною структури (антипатерн задачі 1: тіло перекодованим рядком).
2. **1С читає це без зусиль.** `ЧтениеJSON` розбирає обмін, а `Base64Значение(...)` повертає `ДвоичныеДанные`
   тіла. Знеособлений запис ляже в макет типу `ДвоичныеДанные` так само, як зразки файлових читачів; транспорт відтворення
   віддасть читачу ті самі байти, що дав би справжній HTTP.
3. **Один обмін — один файл.** Тест кличе конектор на одному сценарії, тож перелік `exchanges` дає потрібні файли за
   `scenario`, і не доводиться вантажити весь прогін.
4. **Порядок явний.** Відтворення йде за `seq`, а не за іменами файлів чи часом зміни.
5. **Видно, що саме збережено.** Відсутність поля `headers` запиту очевидна в самій схемі; інвентар полів малий, і білий
   список заголовків відповіді читається в одному місці коду (`Select-AllowedHeaders`).

HAR відкинуто: він несе заголовки запиту (отже, токени), час сервера, куки й багато зайвого, а його тіло — рядок.

## Що від формату потрібно споживачам

**Знеособлювач (задача 2).** Розкодовує `bodyBase64` у байти, знеособлює за кодуванням тіла, кодує назад і перераховує
`bodyLength`. Знеособлює також `request.path` і `request.query` (там IBAN і ідентифікатор рахунку monobank ФОП).
Не змінює `seq`, `scenario`, `status`, `headers`, `failure.kind`. Перевірки а/б/в (D22) — по розкодованих тілах і в усіх
кодуваннях, зокрема по розкодованих `\uXXXX`.

**Транспорт відтворення (задача 3).** Віддає відповіді за порядком `exchanges`; для перевірки зіставляє `method`, `path`
і `query` запиту конектора з записаними (з урахуванням, що знеособлення міняє значення рахунків, а не структуру). Збій
мережі відтворює як відповідь з ознакою збою (D36 п. 1), без заголовків запиту в тексті.

## Сценарії і їхні імена

Поле `scenario` — стабільний ідентифікатор сценарію рекордера (`privat_a1_tx_work_limit`, `corp_a1_daily_windows`,
`fop_client_info_then_statement_immediately`, `*_errors_*` тощо). Частина `aN` — номер рахунку з конфігурації. Перелік
і сенс кожного — у `README.md`.

## Інваріанти, які перевіряє самотест

* у жодному записаному файлі, у жодному кодуванні (UTF-8, UTF-16LE/BE, cp1251, cp866, Base64, URL-кодування,
  `\uXXXX`), не трапляється значення токена з конфігурації — ні в сирому файлі, ні в розкодованому `bodyBase64`;
* заголовки відповіді поза білим списком у запис не потрапляють, а текст збою позбавлений значень секретів;
* шлях запиту входить до білого списку читання (`GET`, три хости).
