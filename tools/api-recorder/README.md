# Рекордер відповідей API банків

Скрипт для власника: записує справжні відповіді чотирьох API на ваших рахунках, щоб конектори платформи
завантаження виписок (етап 5а) перевірялись на реальних даних, а не на припущеннях з документації.

* ПриватБанк — «Автоклієнт» (`acp.privatbank.ua`);
* monobank для юросіб — corp-api (`corp-api.monobank.ua`);
* monobank ФОП — персональне API (`api.monobank.ua`);
* ПУМБ — Vega/VegaNet (`auth.fuib.com` для токена, `service.fuib.com:4103` для читання); працює окремо від трьох інших, див. розділ «ПУМБ».

**У банку скрипт лише читає.** Жодних платежів, вебхуків, змін налаштувань. Це забезпечено в коді, а не обіцянкою:
дозволені лише методи й шляхи читання з білого списку (`ApiRecorder.Lib.ps1`): `GET` для Привату й monobank, а для ПУМБ ще три `POST`,
які банк вимагає для читання (форма на токен-ендпоінт, `searcher`, `period-transactions`). Будь-що інше скрипт відмовляється
надсилати; платіжні методи ПУМБ (`/document/payment/order` та будь-який `document/*/order`) відхиляються окремим правилом. Запити, які могли б щось змінити, у скрипті відсутні.

Файли поруч:

| Файл | Що |
|---|---|
| `Invoke-ApiRecorder.ps1` | Сам рекордер (+ режими `-DryRun` і `-SelfTest`). |
| `ApiRecorder.Lib.ps1` | Спільні функції: білі списки, запис обмінів, пошук токенів. |
| `config.template.psd1` | Шаблон конфігурації із заглушками (єдине, що лежить у git). |
| `FORMAT.md` | Опис формату запису (для знеособлювача й транспорту відтворення). |

## Де що лежить і чому

| Що | Де | Чому там |
|---|---|---|
| Код, шаблон, README, формат | `tools/api-recorder/` у git | це інструмент, він публічний |
| **Ваша конфігурація з токенами** | `R:\github\SMP_BankExchange\temp\api-recorder\config.psd1` | `temp/` гітігнорована; файл читаєте тільки ви |
| **Записи** | `R:\github\SMP_BankExchange\temp\api-recordings\<банк>\<мітка прогону>\` | див. нижче |
| Суми й ідентифікатори для звірки | `R:\github\SMP_BankExchange\temp\api-recorder\owner-only\<банк>\<мітка>\reconcile.txt` | лише вам; **поза текою записів**, яку читає агент, поряд із конфігурацією |

Записи й конфігурація лежать в **основному дереві**, а не поряд зі скриптом, свідомо: записи — це ваша праця
(справжні відповіді банків, які неможливо відтворити за потреби), вони знадобляться й етапу 5б, а робоче дерево
(ворктрі) цього плану тимчасове й буде видалене після злиття. Шляхи можна змінити параметрами скрипта
(`-Config`, `-OutRoot`, `-OwnerRoot`), але за замовчуванням — саме ці.

**Запуск без `-Config` і підтвердження.** Справжній конфіг (з токенами) за замовчуванням читається лише після вашого підтвердження: у консолі рекордер спитає
«Прочитати справжній конфіг <шлях>? [y/N]» — потрібно відповісти `y` (одне підтвердження на запуск; будь-що інше — відмова). Якщо сесія неінтерактивна (stdin перенаправлений,
`pwsh -NonInteractive`, запуск із конвеєра чи від агента), без `-Config` рекордер **відмовляє з кодом 4 і файл не відкриває**. Явний `-Config <файл>` підтвердження не потребує.
Це не стосується `-SelfTest`: він конфіг не читає. Шлях за замовчуванням можна підмінити змінною середовища `SMP_APIRECORDER_DEFAULT_CONFIG` (її ставить самотест на файл-пастку); для вас змінна не потрібна: немає або порожня — шлях, наведений вище.

Чернетка конфігурації вже лежить на місці (копія шаблону із заглушками): лишається вписати значення.

## Що потрібно

* PowerShell 7.5 або новіший (`pwsh`). Нічого більше ставити не треба.
* Токени (див. нижче) і IBAN рахунків.
* Доступ до інтернету з тієї машини, з якої дозволено токен (для Автоклієнта в токена можуть бути IP-обмеження).

## Що вписати

Відкрийте `R:\github\SMP_BankExchange\temp\api-recorder\config.psd1` і замініть заглушки `<ВПИШІТЬ_…>` (разом з
кутовими дужками) на значення в одинарних лапках. Для кожного банку:

* токен (і ідентифікатор для Привату), IBAN рахунків;
* **період** (`Period`): дві дати `РРРР-ММ-ДД` включно, до сьогоднішнього дня. Беріть період, де є кілька десятків
  операцій, а на якусь добу — більше, ніж розмір малої сторінки;
* за бажанням — **період зі скасуванням чи поверненням** (`ReversalPeriod`): період, у якому банк повертав або
  анулював операцію. Це вирішує, як платформа розуміє повернення. **Не пам'ятаєте — залиште заглушки:** сценарій
  буде пропущено, нічого вигадувати не треба;
* для monobank ФОП — за бажанням **насичений період** (`SaturatedPeriod`, найкраще кілька сотень операцій за 31 добу);
* у блоці `Scenarios` — які сценарії вмикати.

Банк, який вам не потрібен, вимкніть: `Enabled = $false`. Банк із незаповненою заглушкою рекордер **не запускає**:
пише, що саме не заповнено, і переходить до наступного (код виходу 2).

## Як запускати

З теки `tools/api-recorder` (в консолі `pwsh`):

```powershell
# 1. Перевірка самого рекордера, без мережі й без ваших токенів (займає секунди)
pwsh -NoProfile -File .\Invoke-ApiRecorder.ps1 -SelfTest

# 2. План запитів без мережі: що буде надіслано і скільки це триватиме
pwsh -NoProfile -File .\Invoke-ApiRecorder.ps1 -DryRun

# 3. Справжній прогін (один банк, щоб спробувати)
pwsh -NoProfile -File .\Invoke-ApiRecorder.ps1 -Bank privat

# 4. Усі ввімкнені банки
pwsh -NoProfile -File .\Invoke-ApiRecorder.ps1
```

`-Bank` приймає `privat`, `monoCorp`, `monoFop`, `pumb`, `all`; **`all` ПУМБ не включає** — вхід у банк лише за явним `-Bank pumb`. Інші параметри: `-RunLabel` (мітка прогону = назва теки,
за замовчуванням дата й час), `-Config`, `-OutRoot`.

**Скільки триває.** ПриватБанк і monobank юросіб — хвилини (пауза ~1 с між запитами). **monobank ФОП — повільний:**
банк дозволяє виписку не частіше ніж раз на 60 секунд, тож між запитами рекордер чекає 61 с; кілька відрізків
періоду плюс сценарії помилок — це десятки хвилин. Скільки саме, показує `-DryRun` (рядок «сумарні паузи»).
Прогін можна запускати на тлі й іншою роботою; не закривайте вікно.

## Що робить рекордер у банку

Лише `GET`. Повний перелік шляхів — білий список у коді; сенс і джерело кожного:

| Банк | Шлях | Для чого | Документація |
|---|---|---|---|
| ПриватБанк | `/api/statements/settings` | серверні дати, фаза, ознака регламенту | розділ «Отримання серверних дат» |
| | `/api/statements/balance` (також `/interim`, `/final`) | баланси | «Отримання балансів і транзакцій за рахунками» |
| | `/api/statements/transactions` (також `/interim`, `/final`) | транзакції: `acc`, `startDate`, `endDate`, `followId`, `limit` | там само |
| monobank юросіб | `/ext/v1/accounts` | список рахунків | специфікація corp-api v1.0.2 |
| | `/ext/v1/accounts/{iban}/balances` | баланси з `isFinal` | там само |
| | `/ext/v1/statement/{iban}/{from}/{to}` | виписка (`limit`, deprecated `direction`) | там само |
| monobank ФОП | `/personal/client-info` | рахунки; звідси береться ідентифікатор рахунку | персональне API v250818 |
| | `/personal/statement/{id}/{from}/{to}` | виписка | там само |

**Ліміти.** Приват — пауза 1,2 с між запитами (рекомендація банку ≤ 1 запит/с); якщо `/settings` повідомляє, що йде
регламент (`work_balance = Y`), Приват зупиняється. monobank юросіб — 1,5 с між запитами, а коли банк у заголовках
повідомляє про вичерпаний ліміт, рекордер чекає, скільки він просить. monobank ФОП — 61 с між запитами, відрізки
не довші за 31 добу. Ліміти навмисно **не провокуються**; якщо банк усе ж відповів `429`, відповідь записується, рекордер
чекає `retry-after` (або 60 с) і повторює запит **один раз**; другий `429` зупиняє сценарій.
*Єдиний виняток — сценарій `fop_client_info_then_statement_immediately`:* це вимір D36 п. 9 (чи видає банк виписку
одразу після `client-info`). Рівно **один** запит виписки без паузи й без повтору; якщо банк відповість `429`,
відповідь лише записується, сценарій завершується без очікування й повтору, і це результат виміру. Вимкнути
можна: `ClientInfoThenStatement = $false`.

**Свідомі помилки** не змінюють нічого в банку: вигаданий недійсний токен (захардкожене очевидно фальшиве значення, не
ваше), початок пізніше за кінець, майбутній період, неіснуючий («чужий») рахунок.

## Сценарії

Скрізь `aN` — номер рахунку з вашого списку.

**ПриватБанк:** `privat_settings`; `privat_aN_balance_period`, `_balance_interim`, `_balance_final`;
`_tx_small_limit` (малий `limit`, кілька сторінок), `_tx_work_limit`, `_tx_default_limit` (без `limit`),
`_tx_no_enddate` (без `endDate`), `_tx_acc_full_iban` (`acc` повним IBAN; основні сценарії йдуть з 14 останніми цифрами,
як у попередника), `_tx_interim`, `_tx_final`, `_tx_charset_cp1251`, `_tx_reversal_period`; помилки `privat_errors_*`.

**monobank юросіб:** `corp_accounts`; `corp_aN_balances`; `_statement_limit500` і `_statement_small_limit` (сторінки
зсувом верхньої межі, як у попередника); `_statement_order_default|UP|DOWN`; `_daily_windows` (запит на кожну добу —
еталон повноти); `_statement_reversal_period`; помилки `corp_errors_*`.

**monobank ФОП:** `fop_client_info_then_statement_immediately`; `fop_statement_segment_NN` (відрізки ≤ 31 доби);
`fop_saturated_segment_NN` (читання, доки сторінка непорожня, — скільки операцій банк віддає за раз);
`fop_reversal_segment_NN`; помилки `fop_errors_*`.

## ПУМБ (Vega/VegaNet)

Окремий блок `Pumb` у конфігурації й окремий банк `-Bank pumb`. На відміну від інших трьох, ПУМБ вимагає **вхід** (логін і пароль користувача
інтернет-клієнт-банку), тож є два запобіжники, яких немає в інших банків.

### Перед першим запуском: відповідь на питання В2 і ключ «вхід погоджено»

Рекордер входить у ПУМБ так само, як робоча інтеграція: `grant_type=password` на `auth.fuib.com` (логін, пароль, `client_id`, `client_secret`).
Тому **спершу відповідайте на питання планувальника (В2): чи не заважає такий вхід робочій інтеграції** (наприклад, обмеження одночасних
сесій користувача) і чи є ліміт сесій. Лише після відповіді «так, не заважає» впишіть у блок `Pumb` конфігурації `LoginApproved = $true`.
За замовчуванням у шаблоні стоїть `$false`, і з ним рекордер до банку **не звертається** (код виходу 2, повідомлення «Вхід у банк не погоджено»).
Ключ виставляє лише власник; агент і скрипти його не вмикають. Підходить тільки булеве `$true` (рядок `'true'` і число `1` не діють).

### Що вписати в блок `Pumb`

* `ClientId`, `ClientSecret` — із файлу налаштувань, який видав банк (`settings.txt` у теці «ПУМБ / PUMB_API»); значення переписуйте як є;
* `Login`, `Password` — логін і пароль користувача інтернет-клієнт-банку (того самого, під яким працює інтеграція);
* `Accounts` — повні IBAN (UA + 27 цифр); `accountId` рекордер знайде за IBAN сам. Валютний рахунок додавайте, лише якщо вирішили його брати (питання В4): для нього додасться запит із типом `CUR`. **Не знаєте, які рахунки є, — `Accounts = 'all'`:** рекордер візьме всі рахунки з відповіді `/account` (гривневі й валютні) і проганяє для кожного ті самі сценарії; `MaxAccounts` (за замовчуванням 10) обмежує їх кількість — беруться перші за порядком відповіді. У консоль і `summary-agent.txt` IBAN, `accountId` і назви не потрапляють, лише кількості (самоперевірка шукає їх там і дає код 3, якщо знайде);
* `Period` — дві дати `РРРР-ММ-ДД` включно, до сьогоднішнього дня. Беріть період, де операцій більше за `SmallPageSize` (щоб було кілька сторінок) і є і вхідні, і вихідні;
* за бажанням `SaturatedPeriod` (найдовший період із найбільшою кількістю операцій) і `ReversalPeriod` (період із поверненням; не пам'ятаєте — заглушки, сценарій пропуститься);
* `Scenarios` — які сценарії вмикати.

### Що рекордер робить у банку (лише читання)

| Хост | Метод і шлях | Для чого |
|---|---|---|
| `auth.fuib.com` | `POST /auth/realms/VegaNet/protocol/openid-connect/token` | токен (один вхід на прогін; повторний вхід лише після 401 або коли строк дії токена добігає кінця, не більше трьох) |
| `service.fuib.com:4103` | `GET /war_veganet_api/account` | рахунки, пошук `accountId` за IBAN |
| | `POST /war_veganet_api/document/searcher` | операції: кілька сторінок і робоча сторінка, без `pagingRequest`, різні фільтри станів і типів, форми `pagingRequest`, формат дат |
| | `POST /war_veganet_api/document/period-transactions` | ті самі операції іншою операцією, щоб порівняти повноту, ідентифікатор і межі |

Платіжні й будь-які змінювальні методи (`/document/payment/order`, `document/*/order`, видалення, підпис тощо) рекордер **відхиляє**: це перевіряє
самотест, і він падає, якщо заборонений метод пройшов.

**Свідомі помилки (безпечні для рахунку):** вигаданий недійсний `access_token`; **вигадані** логін, пароль і `client_secret` (**не ваш логін із хибним паролем** — це
ризик блокування облікового запису; єдиний такий запит іде з очевидно вигаданим логіном `invalid-user-for-recorder`); `fromDate` пізніше за `toDate`;
майбутній період; вигаданий `accountId`; тіло запиту не JSON. Справжній вхід робиться **один раз без повторних спроб**: якщо він не вдався, прогін зупиняється.

### Що потрапляє в запис, а що ні

* **Тіло запиту автентифікації** (пароль, секрет) у запис не потрапляє: у файлі лише ознака `bodyOmitted` з причиною. Решта тіл запитів (дати, `accountId`, `pagingRequest`) — як пішли.
* **Відповідь автентифікації** (`access_token`, `refresh_token`, `session_state` тощо) записується **замаскованою**: кожне значення замінено маркером тієї ж довжини й форми
  (літери → `a`/`A`, цифри → `9`, розділювачі лишаються); `token_type`, `scope`, числа й форма помилки (`error`) читабельні. Справжнє тіло автентифікації ні в запис, ні в консоль не потрапляє.
* Заголовків запиту (зокрема `Authorization`) у записі немає взагалі.

### Самоперевірка для ПУМБ і консольний журнал

Крім значень з конфігурації (`ClientId`, `ClientSecret`, `Login`, `Password`) рекордер шукає й **значення, які видав банк у цьому прогоні** (токени, `session_state`), у всіх кодуваннях, у всіх файлах запису
**і в консольному журналі**: вивід прогону ПУМБ дублюється у файл `console.log` у теці запису, і він скануватиметься разом із рештою. Хочете перевірити ще й `stderr` — перенаправте його у файл і назвіть цей файл у `-StderrLog`
(його теж буде проскановано; файл лежить поза текою запису):

```powershell
pwsh -NoProfile -File .\Invoke-ApiRecorder.ps1 -Bank pumb -RunLabel <мітка> -StderrLog "$env:TEMP\pumb-stderr.log" 2> "$env:TEMP\pumb-stderr.log"
pwsh -NoProfile -File .\Invoke-ApiRecorder.ps1 -CheckRun -Bank pumb -RunLabel <мітка> -StderrLog "$env:TEMP\pumb-stderr.log"
```

Виданих банком значень після прогону вже немає, тож `-CheckRun` перевіряє лише значення з конфігурації; динамічну перевірку робить сам прогін. Знайдено щось — код 3: теку **нікому не передавати**.
Якщо файл `-StderrLog` не вдалося прочитати, це теж «самоперевірка не виконана» (код 3), а не «чисто».

### Порядок для власника (коротко)

1. `pwsh -NoProfile -File .\Invoke-ApiRecorder.ps1 -SelfTest` — код 0 (без мережі й без ваших даних).
2. Відповідь на В2 і В4 (від планувальника) → `LoginApproved = $true`, рахунки й період у конфігурації.
3. `pwsh -NoProfile -File .\Invoke-ApiRecorder.ps1 -DryRun -Bank pumb` — план запитів без мережі.
4. `pwsh -NoProfile -File .\Invoke-ApiRecorder.ps1 -Bank pumb -RunLabel run1`.
5. `-CheckRun`, звірка сум із кабінетом (`owner-only\pumb\<мітка>\reconcile.txt`), далі передати теку запису планувальнику. `run2` — через ≥ 1 робочий день, `run3` — межі й насичений період (`BoundaryPairs = $true`).

## Повторний прогін

Щоб побачити, чи ідентифікатори операцій лишаються тими самими після проміжної виписки (Приват) і після
`hold`/`PENDING` (monobank), потрібен **повторний прогін тих самих періодів щонайменше через один робочий день**.
Нічого міняти не треба: той самий скрипт, той самий конфіг, нова мітка прогону. (Кожна мітка — окремий вимір;
перелік зроблених прогонів і що кожен показав — у журналі плану, а не тут.)

```powershell
pwsh -NoProfile -File .\Invoke-ApiRecorder.ps1 -RunLabel <нова мітка>
```

### Що дописати у свій конфіг для повторного прогону

Ваш `config.psd1` уже заповнений і **не перезаписується**; нові ключі необов'язкові. Для повторного прогону бажано
виміряти, скільки операцій банк віддає за одну сторінку, тож допишіть **найдовший період з найбільшою кількістю
операцій** (кілька сотень і більше) для юросіб і ФОП, і, якщо пам'ятаєте, період із поверненням/скасуванням. Нічого не
вигадуйте: немає такого періоду — не пишіть. Вставте у відповідний блок (`MonoCorp` або `MonoFop`) поряд із `Period`, а в
його `Scenarios` додайте перемикач; дати `РРРР-ММ-ДД`, обидві включно, до вчорашнього дня (для ФОП — довільної довжини,
рекордер сам ріже на відрізки по 31 добі, кожен — 61 с паузи, тож довгий період означає довгий прогін):

```powershell
        # у блоці MonoCorp (юросіб), після Period:
        SaturatedPeriod = @{ From = '2026-01-01'; To = '2026-01-31' }
        ReversalPeriod  = @{ From = '2026-02-10'; To = '2026-02-12' }   # необов'язково, якщо пам'ятаєте
        # ...а в його Scenarios:
        #   Saturated = $true

        # у блоці MonoFop (ФОП), після Period:
        SaturatedPeriod = @{ From = '2026-01-01'; To = '2026-03-31' }
        ReversalPeriod  = @{ From = '2026-02-10'; To = '2026-02-12' }   # необов'язково
        # ...а в його Scenarios (якщо там уже є Saturated = $true — нічого додавати не треба):
        #   Saturated = $true
```

(Дати вище — лише приклад формату, підставте свої.) Без `SaturatedPeriod` або без `Saturated = $true` сценарій просто
вимкнено, помилки не буде; `-DryRun` покаже, що саме ввімкнено. Сценарій юросіб називається
`corp_aN_statement_saturated_limit500`, а розміри сторінок банку видно в `summary-agent.txt` (рядок «розмір сторінки»).

Тека з міткою, яка вже є, не перезаписується (скрипт відмовиться й попросить іншу мітку). Корисно, щоб у перший прогін
потрапили операції «на сьогодні/вчора» (проміжна виписка), інакше їхній перехід у підсумкову не буде видно: тому
`Period` краще закінчувати вчорашнім днем, а перший прогін робити ввечері або вранці після нього.

## run3: межі запиту й насичені періоди

Прогін `run3` вимірює речі, яких у `run1`/`run2` не було видно (спека D36 п. 11). Його сценарії **вимкнені за
замовчуванням** і вмикаються перемикачами в `Scenarios` вашого `config.psd1`:

| Перемикач | Блок | Що робить |
|---|---|---|
| `DatKlBoundary` | `Privat` | Вимір, до якого дня банк відносить операцію, у якої день `DAT_KL` відмінний від дня `DAT_OD`. Рекордер бере операції `TxWorkLimit` цього прогону (усі сторінки; без нього — один запит `…_datkl_source`), обирає операцію з різними днями `DAT_KL` і `DAT_OD` (з кількох — найдалі від меж періоду), і запитує транзакції за один день `DAT_OD` (`startDate` = `endDate`), з тими ж `acc` і `limit`. Сценарій `privat_aN_datkl_boundary`. Немає такої операції — збій `no_candidate`, запиту немає. Чи є кандидат у відповіді, рекордер не перевіряє. |
| `StatementSmallLimitOverlap` | `MonoCorp` | Той самий період і малий `limit`, що `StatementSmallLimit`, але наступна сторінка просить `to` = найраніша `time` сторінки + 1 (межова секунда потрапляє в наступний запит знову). Сценарій `corp_aN_statement_small_limit_overlap`. У ФОП `limit` немає, тож там цього сценарію немає. |
| `BoundaryPairs` | `MonoCorp`, `MonoFop` | Вимір, чи межі запиту `from` і `to` включні. Рекордер **сам** обирає операцію й робить чотири запити: `from` = t та t − 1, `to` = t та t + 1. Сценарії `{corp_aN\|fop_a1}_boundary_{from\|to}_{eq\|shift}`. |
| `Saturated` | `MonoCorp` | Насичений період юросіб (`SaturatedPeriod`): `limit=500` до неповної сторінки, продовження з `to` = найраніша `time` + 1, збіг запитів — збій `stuck_cursor`. Сценарій `corp_aN_statement_saturated_limit500`. У run1/run2 не вмикався, тож старого способу (`to` = найраніша) для юросіб немає. |
| `SaturatedOverlap` | `MonoFop` | Насичений період ФОП: запити виписки до сторінки, коротшої за 500, продовження з `to` = найраніша `time` + 1, пауза 61 с. Сценарій `fop_a1_saturated`. Потрібен `SaturatedPeriod`. |

**Що вписати.** Перемикачі (`$true`) і період `SaturatedPeriod` (юросіб і ФОП) (дві дати `РРРР-ММ-ДД`, до вчорашнього дня;
найкраще період, на якому за 31 добу кілька сотень операцій, довший теж можна — рекордер різатиме на відрізки по 31 добі).
Порожній `SaturatedPeriod` (заглушки) не помилка: сценарій ФОП `fop_a1_saturated` буде пропущено, у `summary-agent.txt` з'явиться
рядок «пропущено» (для юросіб — рядок «[вимкнено]» у консолі). **Значень операцій вписувати не треба й не можна** — ні часу, ні сум, ні ідентифікаторів: для пар меж
рекордер обирає операцію сам.

**Як рекордер обирає операцію для пар меж.** Бере відповіді звичайного виписочного сценарію **цього ж прогону** за основний
період (юросіб — `statement_limit500`, ФОП — `statement_segment_NN`; якщо їх у прогоні немає, робить один запит
`…_boundary_source`: юросіб — `limit=500` за період, ФОП — перша сторінка першого відрізка). Серед усіх прочитаних операцій
шукає ту, що **єдина у своїй секунді `time`** й лежить на сторінці, **не повній** за лімітом (юросіб — коротшій за `limit`
запиту, ФОП — коротшій за 500): повна сторінка могла обрізати операції, тож межа на ній не показова. З придатних бере ту, що
найдалі від найближчої іншої операції. Не знайшов — пише збій `no_candidate` у сценарії `…_boundary_candidate` і пар не
робить (тоді оберіть для `Period` період із кількома десятками операцій, розкиданих у часі, і повторіть). Якщо читання за
`limit` зупинилось через повну сторінку в одній секунді, рекордер пише збій `stuck_cursor` — це результат виміру, а не
помилка рекордера. Висновку про включність меж рекордер не робить: він лише записує обміни, аналіз — пізніше (див. `FORMAT.md`).

**Скільки триває.** Кожен запит виписки ФОП — 61 с. Орієнтир: `client-info` 1 + пари меж 4 (+1 `boundary_source`, якщо
`StatementSegments` вимкнено) + насичений період (не менше однієї сторінки на відрізок по 31 добі, плюс по одній на кожну
повну сторінку; стеля `MaxSaturatedPages`, за замовчуванням 40) — для насиченого періоду в три місяці це близько 10–12
запитів, тобто 10–13 хвилин. Якщо лишити ввімкненими й старі сценарії ФОП, додайте по 61 с на кожен їхній запит (відрізки
основного періоду, помилки, `ClientInfoThenStatement`) — для швидкого `run3` їх краще вимкнути. Юросіб: `small_limit_overlap` —
стільки ж запитів, скільки `small_limit` (до `MaxSmallPages`, по ~1,5 с, тобто до півтори хвилини), пари меж — 4–5 запитів на
рахунок (секунди). Точніше покаже `-DryRun` (рядок «сумарні паузи»; на заглушках сторінок менше, ніж у справжньому прогоні,
а кандидата для пар підставлено синтетичного).

Запуск — як звичайно, з новою міткою: `pwsh -NoProfile -File .\Invoke-ApiRecorder.ps1 -RunLabel run3`.

## Безпечна форма запуску не власником

Рекордер запускає власник. Якщо власник **прямо доручив** прогін агентові, діє безпечна форма, що не
дає агентові побачити ні токенів, ні сум:

* агент не відкриває `config.psd1` і теку `owner-only`; токени скрипт читає лише в пам'ять. Виняток: якщо власник
  прямо доручив дописати параметри, скрипт читає конфіг у пам'ять і друкує лише назви змінених ключів. Перед правкою
  він робить резервну копію, а видаляє її власник. Про таку правку пишеться рядок у журнал;
* сирі записи й мапу знеособлення агент читає лише скриптом, що маскує поля на вході й друкує кількості, класи
  символів чи маски. Значень він не цитує ні у виводі, ні в журналі, ні в повідомленнях. Маскувати треба саме на вході:
  маска на виході (фільтр виводу на кшталт `sed`) одного разу не спрацювала й пропустила значення у вивід;
* вивід консолі (суми, ідентифікатори, IBAN) переспрямовується у файл у `owner-only`, а не в канал, який
  бачить агент: `pwsh -NoProfile -File .\Invoke-ApiRecorder.ps1 -RunLabel <мітка> *> <OwnerRoot>\<банк>\<мітка>\console.txt`
  (теку створює власник або скрипт; шлях поза текою записів);
* агентові лишаються код виходу (таблиця нижче) і `summary-agent.txt` (лише кількості);
* перерваний прогін перевіряється `-CheckRun` (розділ «Самоперевірка»), як і звичайний.

Це лише форма запуску: доручення власника на кожен прогін обов'язкове, «безпечна» не означає «без дозволу».

## Що звірити з кабінетом

Після прогону в консоль і в файл `owner-only\<банк>\<мітка>\reconcile.txt` (поза текою записів) виводяться кількості й суми за сценаріями
й валютами (надходження/списання, за станами операцій) і баланси. Порівняйте основні сценарії (`*_tx_work_limit`,
`*_statement_limit500`, `*_daily_windows`, `fop_statement_segment_*`) з випискою в кабінеті банку за той самий період:
кількість операцій і суми мають збігатися. Розбіжність — це і є цінна знахідка, повідомте її планувальнику.

## Самоперевірка: токенів у записах немає

Після кожного прогону (також перерваного Ctrl+C чи винятком: самоперевірка стоїть у `finally`, стан запису — `interrupted`) рекордер **сам шукає значення кожного токена з вашої конфігурації в кожному записаному файлі**
(включно з розкодованими тілами відповідей) у всіх кодуваннях: UTF-8, UTF-16 (LE/BE), cp1251, cp866, Base64 (будь-яке
вирівнювання), URL-кодування, `\uXXXX`. Якщо знайдено — прогін позначається проваленим (код виходу 3), у консолі
й у файлі `LEAK-DETECTED.txt` названо файл і форму (самого значення не друкується), а теку **не передавайте нікому**;
токен краще перевипустити в банку. Якщо знайдено «ідентифікатор» Привату, це може бути випадковий збіг із числом у
відповіді; повідомте планувальнику, не пишучи значення.

У режимі `-SelfTest` рекордер перевіряє сам пошук без мережі й без ваших токенів: пише файли з вигаданим помітним
значенням у різних кодуваннях і мусить знайти кожне, а на чистих файлах — нуль; ненульовий код виходу означає промах.
Запустіть його перед першим прогоном.

Справжній Ctrl+C не перевірено, тож після переривання вручну запустіть перевірку теки перерваного прогону (без
мережі; читає вашу конфігурацію лише в пам'ять, перевіряє теку запису й відповідну теку `owner-only`, значень не
друкує; код 0 — чисто, 3 — знайдено, 2 — не вдалося, зокрема конфігурація без жодного токена):

```powershell
pwsh -NoProfile -File .\Invoke-ApiRecorder.ps1 -CheckRun -Bank privat -RunLabel <мітка прогону>
```

(`-Bank` — `privat`, `monoCorp`, `monoFop`, `pumb` або `all`; `-OutRoot`/`-OwnerRoot`/`-Config` — як у прогоні; для `pumb` додайте `-StderrLog`, якщо перенаправляли stderr, див. розділ «ПУМБ».)

Крім пошуку, токен у запис не може потрапити структурно: заголовків запиту в записі немає, з відповідей беруться лише
дозволені заголовки (`FORMAT.md`).

## Що кому передавати

* **Агенту (через планувальника) — теку запису** `…\api-recordings\<банк>\<мітка>\` разом із `summary-agent.txt`:
  там лише кількості (статуси HTTP, сторінки, операції за станами), без сум, ідентифікаторів, IBAN, імен.
* **Не передавайте** теку `owner-only` (суми й ідентифікатори), файл `config.psd1` і нічого з консолі з сумами.
* Відповіді банків містять справжніх контрагентів: записи лишаються в `temp/` і в git не потрапляють; у тести вони
  йдуть тільки знеособленими.
