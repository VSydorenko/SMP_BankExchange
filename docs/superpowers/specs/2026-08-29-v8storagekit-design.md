# SMP_V8StorageKit — дизайн внутрішнього рішення для конвеєра «сховище ↔ git»

Дата: 2026-08-29. Статус: затверджено в обговоренні, чекає на ревʼю спеки.
Походження: перезапуск BankExchange (`2026-08-28-bankexchange-restart-design.md`) побудував
конвеєр, придатний для всіх 1С-рішень власника; тут — дизайн його упаковки в
перевикористовуване рішення.

## 1. Проблема і мета

`SMP_BankExchange` має робочий контур «сховище конфігурацій ↔ git»: скрипти `tools/`
(синхронізація, вивантаження, розкатка, збірка), тести до них, guard-логіку, конвенції
репозиторію (розкладка, EOL-політика, дозволи, CLAUDE.md) і документовану архітектуру.
Мінімум вісім інших 1С-репозиторіїв ведуться так само (сховище + розширення + кілька
конфігурацій) і мають отримати той самий контур **без повторної розробки скриптів, тестів
і всього спільного**.

Мета — рішення, за якого користувач відкриває будь-який свій 1С-проєкт, пише промпт
природною мовою («перенеси нові версії сховища в git», «підключи цей репозиторій до
конвеєра»), і агент або однозначно розуміє, що і з якими параметрами запускати, або ставить
питання рівно про те, чого не може вивести сам.

Анти-мета: **не** будувати каркас, що дублює механізми Unica. Kit покриває рівно те, чого
Unica не робить (контур «сховище → git», replay історії з авторством, конвенції репо);
метадані, форми, СКД, borrow, збірка через v8-runner лишаються за плагіном `unica`.
`build.ps1` входить у kit лише тому, що `make` Unica на Windows fail-closed
(«Отказано в доступе, os error 5»).

## 2. Що показала розвідка (2026-08-29)

Оглянуто всі девʼять репозиторіїв-кандидатів. Висновки, що визначають дизайн:

- **Жоден ще не в схемі BankExchange.** Вісім 1С-репо — у старій структурі gitsync-ери:
  EDT-вихідники (`.mdo`), квартет `AUTHORS` + `VERSION` + `DT-INF/` + `ConfigDumpInfo.xml`.
  Ніде немає `v8project.yaml`, `storage.json`, `tools/`, `CLAUDE.md`. Тобто половина
  цінності kit — **процедура міграції**, а не лише щоденна експлуатація.
- **Відбиток старого формату — квартет файлів**, не конфіг gitsync (той жив поза деревом).
  Автовиявлення в скілах ключиться на квартет.
- `SMP_SimplyOrders` — не 1С (Next.js), зі списку випадає. Лишаються вісім.
- `SMP_SimplyConnect`: продукт `SimplyConnect_SMB` (`VERSION` 47), порожній плейсхолдер
  `SimplyConnect_SMBru`, C++-аддін (мігрував в окремий репозиторій — ігнорується).
- **Сім репо ділять один кореневий коміт 2019 року** і тягнуть по ~690 МБ мертвої історії
  повної конфігурації при робочому дереві в одиниці МБ. Міграція йде через чисту
  replay-гілку (як `restructure/2026-08` у BankExchange), стара історія лишається в старій
  гілці й страхувальному bundle.
- `SMP_SMB_rus_DEV` і `SMP_SMB_ukr_DEV` відстежують **повні конфігурації** (не лише
  розширення) — для них потрібна адаптація конвеєра (див. «Відкриті питання»).
- Локальні git-налаштування (`core.longpaths=true`, `quotepath=false`) у старих репо
  виставлені руками й не переносяться клоном — міграційний скіл має виставляти їх явно.

Перелік для впровадження: `SMP_OnlineExchange`, `SMP_SimplyAutomate`, `SMP_SimplyCatalog`,
`SMP_SimplyConnect`, `SMP_SimplyDelivery`, `SMP_SimplyMarketplace`, `SMP_SMB_rus_DEV`,
`SMP_SMB_ukr_DEV`; еталон і перший споживач — `SMP_BankExchange`.

## 3. Форма рішення: один репозиторій = маркетплейс + плагін

Окремий **публічний** GitHub-репозиторій `SMP_V8StorageKit`, який одночасно є маркетплейсом
Claude Code і містить єдиний плагін (модель — плагін `unica`: маркетплейс
`IngvarConsulting/unica-marketplace`, встановлення у версіонований кеш, user-скоуп).
Локальна робоча копія — `R:\github\SMP_V8StorageKit`.

```
SMP_V8StorageKit/
├─ .claude-plugin/
│  ├─ marketplace.json      маркетплейс з одним плагіном
│  └─ plugin.json           плагін v8storagekit, semver-версія
├─ skills/
│  ├─ storage-pipeline/     щоденний цикл: sync/preview, dump-config, load-ext, build
│  ├─ product-onboarding/   підключення нового продукту в уже мігрованому репо
│  └─ repo-migration/       міграція старого gitsync-репо на нову схему
├─ tools/                   КОПІЯ з SMP_BankExchange/tools (див. §3.1)
│  ├─ storage-sync.ps1  dump-config.ps1  load-ext.ps1  build.ps1
│  ├─ lib/                  PathSafety, V8, StorageReport, Authors, SyncState
│  ├─ tests/                Pester-тести + фікстури (їдуть разом зі скриптами)
│  └─ assets/empty-extension/
├─ templates/               шаблони файлів репо-споживача
│  ├─ CLAUDE.md  .gitattributes  .gitignore
│  ├─ settings.json         дозволи .claude/settings.json
│  └─ storage.json.example
└─ docs/                    узагальнена архітектура контуру «сховище ↔ git»
```

### 3.1 Принцип: копіювання з адаптацією, не повторна розробка

Скрипти, модулі, тести, фікстури і стаб `empty-extension` **копіюються** з
`SMP_BankExchange/tools` як є. Єдина запланована адаптація — параметр `-RepoRoot`
(за замовчуванням — поточна тека) замість якоря `$PSScriptRoot\..`
(`storage-sync.ps1:20`, `dump-config.ps1:18`, `load-ext.ps1:19`, аналогічно `build.ps1`),
бо скрипти більше не лежать усередині репо-споживача. Скрипт перевіряє, що `-RepoRoot` —
корінь git-репозиторію (тека з `.git`), і зупиняється, якщо ні (fail-closed, у дусі наявних
guard-перевірок); перевірка існування самого продукту в скриптах уже є. Будь-які інші зміни — лише коли конкретний репозиторій цього
вимагатиме, окремими комітами kit з поясненням причини.

Контракт `storage.json` (поля `storagePath`, `extensionName`, `lastSyncedVersion`,
`sourcePath`) — **стабільний**: kit його не змінює, щоб репо-споживачі не залежали від
версії плагіна. Перевизначення `storagePath` через `v8project.local.yaml` працює як зараз.

### 3.2 Канонічна форма виклику

Скіли завжди викликають скрипти в одній формі:

```powershell
pwsh "$env:CLAUDE_PLUGIN_ROOT/tools/storage-sync.ps1" -RepoRoot . -Product <Продукт>
```

`${CLAUDE_PLUGIN_ROOT}` підставляється під час виконання і не залежить від версії плагіна в
кеші — вшитих шляхів немає. `-Apply` додається **лише** коли користувач явно попросив
виконати (правило з CLAUDE.md BankExchange успадковується всіма споживачами через шаблон).

## 4. Межі (успадковані й нові)

- Сховища конфігурацій — **тільки читання**; запис у сховище виконує людина в Конфігураторі.
  Жодних `ConfigurationRepositoryCommit`/`Lock`/`UnlockObjects` — межа переноситься в
  шаблон CLAUDE.md і в документацію kit.
- Мутуючі скрипти без `-Apply` нічого не змінюють.
- Kit публічний: жодних логінів, паролів, рядків підключення, імен серверів у kit і в
  шаблонах. Виняток `storagePath` у `storage.json` споживача — політика та сама, що в
  BankExchange (`docs/architecture/storage-and-git.md`).
- Kit не обгортає Unica: воркспейси `v8project.yaml` створюються за процедурою скіла
  (копія-адаптація підходу BankExchange), але вся робота з метаданими — через плагін `unica`.
- Формат вихідників — Designer platform XML; платформа — гілка 8.3.27.x. Ті самі межі, що в
  BankExchange, бо їх диктують Unica і сховища.

## 5. UX-контракт: як агент розуміє промпти

Ланцюжок розвʼязання параметрів (спільний для всіх скілів): **промпт** (що робити, чи є
`-Apply`-намір) → **маркери репо** (`storage.json` = продукт підключений; квартет
`AUTHORS`+`VERSION`+`DT-INF`+`ConfigDumpInfo.xml` = старий формат, потрібна міграція) →
**питання користувачу** лише про те, чого немає ні в промпті, ні в маркерах.

### 5.1 storage-pipeline (щоденний цикл)

Тригери: «сховище», «синхронізація», «перенеси версії», «вивантаж конфігурацію»,
«розкоти розширення», «збери cfe/epf». Скіл: знаходить продукти за `storage.json`
(якщо продуктів кілька і промпт не уточнює — питає), показує прев'ю без `-Apply`,
виконує з `-Apply` тільки на явне прохання. Знання про перший прогін продукту
(два коміти: спершу `storage.json` окремо), про зупинки guard-перевірок і про невідомих
авторів (`AUTHORS`) — переносяться з документації BankExchange у скіл.

### 5.2 product-onboarding (новий продукт у мігрованому репо)

Тригери: «підключи продукт», «додай розширення до синхронізації». Створює теку продукту за
конвенцією `<Продукт>_<КодКонфігурації>` (як `BankExchange_SMB`), `storage.json`,
`v8project.yaml` (+ інструктує про gitignored `v8project.local.yaml`), робить перший коміт
`storage.json` окремо. Питає: шлях до сховища (може запропонувати кандидатів зі сканування
`R:\СховищаРозширень_1С`), ім'я розширення, підключення дев-бази.

### 5.3 repo-migration (старий gitsync-репо → нова схема)

Плейбук по слідах `restructure/2026-08` BankExchange. Кроки: страхувальний bundle старої
історії → локальні git-налаштування (`core.longpaths`, `quotepath`) → закомічені
`.gitattributes` (EOL-політика — та, що тримає guard чистої робочої копії придатним) і
`.gitignore` з шаблонів → чиста гілка → розкладка продуктових тек → `AUTHORS` (наявний файл
переноситься; невідомі імена зупиняють прогін — як у BankExchange) → replay історії сховища
через `storage-sync.ps1 -Apply` → CLAUDE.md і дозволи з шаблонів → доля старого EDT-дерева
(видаляється в новій гілці; стара гілка і bundle лишаються). Питає: replay з версії 1 чи
від поточного `VERSION`; шляхи сховищ; що робити з продуктами-плейсхолдерами (як порожній
`SimplyConnect_SMBru` — підключати зараз чи позначити «пізніше»).

## 6. Встановлення, оновлення, цикл розробки

- **Встановлення** — як будь-який плагін: `claude plugin marketplace add VSydorenko/SMP_V8StorageKit`,
  далі `claude plugin install`, скоуп обирає користувач (природний — user; project/local
  доступні штатно).
- **Оновлення** — явне: `/plugin update`. Встановлена версія зафіксована в кеші, доки
  користувач сам не оновить, — це і є пінування стабільного контуру.
- **Розробка** — у робочій копії `R:\github\SMP_V8StorageKit`, окремою сесією. Живе
  тестування на реальному проєкті: `claude --plugin-dir R:\github\SMP_V8StorageKit` +
  `/reload-plugins` після правок. Готово — пуш, споживачі забирають через `/plugin update`.
  Сабмодулі не використовуються: kit — інструмент оточення, а не build-залежність репо.

## 7. Дозволи в репо-споживачах

Плагіни не вміють постачати правила дозволів, тому шаблон `.claude/settings.json` кладеться
в кожен репо при міграції. Він відтворює політику BankExchange: без запиту — лише читання
(git-перегляд, прогін тестів kit з `-ExcludeTag Integration`, read-only Unica); прев'ю
конвеєрних скриптів і все з `-Apply` — з підтвердженням (префіксні правила дозволили б
`-Apply` автоматично — тому прев'ю свідомо не в allow-списку, як у BankExchange).

Гіпотеза для перевірки на початку реалізації: правило-префікс з літеральним текстом
канонічної форми (`pwsh "$env:CLAUDE_PLUGIN_ROOT/tools/…"`) стабільне між версіями плагіна,
бо текст команди не містить версії. Якщо не підтвердиться — fallback: разове
«allow and don't ask again» після оновлення плагіна; це прийнятно і не блокує дизайн.

## 8. Порядок впровадження

1. **Створення kit** (окремий репозиторій, окрема сесія): копіювання `tools/` з
   BankExchange, адаптація `-RepoRoot`, зелені Pester-тести в kit, скіли, шаблони,
   маркетплейс, встановлення плагіна на цій машині.
2. **BankExchange — перший споживач** (у цьому репозиторії, після того як плагін
   запрацював): **видалити `tools/`** з репо, щоб не було двох конкурентних копій
   механізмів; оновити CLAUDE.md («Типові операції» — на канонічну форму виклику через
   `$env:CLAUDE_PLUGIN_ROOT`; «Дозволи» — на нові префікси) і `.claude/settings.json`.
   Критерій: прев'ю `storage-sync` для всіх трьох продуктів дає той самий результат, що
   давав локальний `tools/` до видалення. `docs/architecture/storage-and-git.md`
   лишається — це документ рішень цього репо; узагальнений зміст переїжджає в `docs/` kit
   на етапі 1 копіюванням-адаптацією.
3. **Пілотна міграція** — рекомендація: `SMP_OnlineExchange` (найменший і найчистіший;
   нюанс — проєкт вкладений у само-іменовану теку, розплющиться при міграції). Проганяється
   цілком через скіли, без ручних команд — це тест UX-контракту.
4. **Решта репозиторіїв** — по одному, кожен своєю сесією; порядок обирає користувач.
   `SMP_SMB_rus_DEV`/`SMP_SMB_ukr_DEV` — останніми (див. відкрите питання про повні
   конфігурації).

## 9. Тестування і критерії приймання

- Тести їдуть у kit разом зі скриптами; `Run-Tests.ps1` працює з кореня kit; інтеграційні
  (`V8.Tests.ps1` з реальним `1cv8.exe`) — за тегом `Integration`, як зараз.
- Адаптація `-RepoRoot` покривається тестом (корінь за замовчуванням, явний корінь,
  відмова на не-корені).
- Приймання етапу 1: зелені тести + встановлений плагін + скіл відповідає на «перенеси нові
  версії» коректною командою в чужому порожньому репо (питає, бо немає `storage.json`).
- Приймання етапу 2: BankExchange без `tools/` проходить повний прев'ю-цикл трьох продуктів.
- Приймання етапу 3: пілотний репо мігровано скілами end-to-end; replay-коміти несуть
  трейлери `Storage-Version`/`Extension-Version`/`Storage-User`.

## 10. Ризики й відкриті питання

- **Повні конфігурації** (`SMP_SMB_rus_DEV` — `cf` УНФ, сховище v346; `SMP_SMB_ukr_DEV` —
  BAS small business, сховище v1041): конвеєр зараз заточений під розширення
  (стаб `empty-extension`, ключі `-Extension`). Підтримка сховищ повних конфігурацій — окрема
  адаптація kit, рішення про неї (і про політику публічності репо з кодом вендора)
  приймається перед етапом 4, не зараз.
- **Гіпотеза про стабільність префіксних правил дозволів** — перевіряється першою на етапі 1;
  fallback описано в §7.
- **Дрейф «останньої версії» kit** — оновлення явне (`/plugin update`), тести їдуть з kit;
  перед оновленням у критичний момент можна лишитись на встановленій версії.
- **~3.4 ГБ дубльованої мертвої історії** в семи репо: міграція не переписує старі гілки,
  але після неї варто окремо вирішити про bundle/архівацію — поза обсягом kit.
