# monobank: два режими — ФОП і ТОВ

**Дата:** 2026-09-15
**Статус:** спека зафіксована; план реалізації — в окремій сесії
**Продукт:** `SMP_BankExchange_SMB` (УНФ, українська). SMBru і ACC — поза обсягом, див. §10
**Гілка:** `feature/monobank-api`
**Передумова:** карта API зафіксована в `docs/banks/monobank-api-map.md`

## 1. Навіщо

Підсистема інтегрована з monobank через **персональне** Open API. Цього достатньо для ФОП і
не вистачає для ТОВ: рахунки юридичних осіб живуть в іншому API, на іншому хості, з іншою
схемою відповіді. Клієнти-ТОВ сьогодні не обслуговуються взагалі.

Паралельно накопичились дефекти чинного ФОП-режиму: зсув часового поясу в запиті, відсутність
пагінації, мовчазні втрати при перевищенні лімітів, [issue #10](https://github.com/VSydorenko/SMP_BankExchange/issues/10)
про призначення платежу, та непрацездатний автоматичний обмін.

Спека охоплює обидва режими одним дизайном, бо вони ділять точку входу, довідник налаштувань,
регламентне завдання і механізм завантаження документів.

## 2. Що встановлено фактично

Перевірено на гілці `feature/monobank-api`, коміт `1bdd463`.

### 2.1 ФОП і ТОВ — це різні API monobank

У monobank п'ять API (закріплене повідомлення офіційної телеграм-групи). Нас стосуються два:

| Клієнт | API | Хост |
|---|---|---|
| ФОП, фізособи | персональне Open API | `api.monobank.ua/personal/*` |
| ТОВ | API рахунків юридичних осіб | `corp-api.monobank.ua/ext/v1/*` |

**ФОП не має доступу до API юросіб** — підтверджено обговоренням у групі (серпень 2026):
«Тільки для тов є підготовка платежу на оплату. Всі інші рід-онлі», «Виключно в ТОВ є така
можливість». Отже обидва режими потрібні постійно, а не як тимчасова сумісність.

Деталі, цитати й повна карта п'яти API — `docs/banks/monobank-api-map.md`.

### 2.2 Призначення платежу для ФОП недоступне

У персональному API `description` описане як «Опис транзакцій», у corp API — як **«Призначення
операції»**. Окремого поля призначення платежу в персональному API немає; набір полів
транзакції ідентичний у персональній, провайдерській і community-специфікаціях.

Наслідок: issue #10 для ФОП не має повного рішення. Максимум — не втрачати те, що банк
віддає, склеївши `description` і `comment`. Для ТОВ призначення є по-справжньому.

### 2.3 Дедуплікація існує, але зламана довжинами

Механізм пошуку існуючого документа вбудований у `СМП_КлиентБанк`
(`DataProcessors/СМП_КлиентБанк/Ext/ManagerModule.bsl:3406-3481`): ключ — день, банківський
рахунок, організація, номер; далі звіряються сума, вид операції, рахунок контрагента.

Реквізит пошуку залежить від виду документа (`ManagerModule.bsl:271-276`):

| Документ | Реквізит пошуку | Довжина |
|---|---|---|
| `ПоступлениеНаСчет` | `НомерВходящегоДокумента` | **20** |
| `РасходСоСчета` | `Номер` | **11** |

Заповнюється з `ИсходныеДанные.НомерДок` (`ManagerModule.bsl:815`, `:1273`), а монобанк-модуль
кладе туди `id` транзакції (`СМП_РаботаСБанкамиМонобанкAPIСервер/Ext/Module.bsl:301`).

Порівняння при пошуку **точне**, без урахування обрізання (`ManagerModule.bsl:3479-3480`):

```bsl
ВыборкаНомер = СокрЛП(ВыборкаДокументов.Номер); // Прав(СокрЛП(ВыборкаДокументов.Номер), ДлинаНомера);
Если ВыборкаНомер = НомерДляПоискаДок
```

Обрізання за довжиною колись було і його закоментували. Звідси:

| Режим | `id` | Куди лягає | Результат |
|---|---|---|---|
| ФОП, вхідні | ~12 символів | 20 | працює |
| ФОП, вихідні | ~12 символів | **11** | обрізається при записі, шукається повний → **дубль щоразу** |
| ТОВ | **UUID, 36** | 20 і 11 | не влазить нікуди → дедуплікації немає |

Довжина `id` персонального API взята з прикладу у специфікації (`ZuHWzqkKGVo=`); банк її не
гарантує. Для ТОВ 36 — це UUID, тут сумнівів немає.

### 2.4 Синхронізація-видалення розрахована на файлову виписку

Після завантаження `Загрузить()` викликає `СинхронизироватьДокументыПоСчетам`
(`ObjectModule.bsl:1916`): документи за завантажені дати, яких немає у виписці, **позначаються
на видалення**.

Це стандартний механізм УНФ (`cf/src/DataProcessors/КлиентБанк/Ext/ObjectModule.bsl:596`,
виклик на `:968`), який ми вже двічі пом'якшили — перевели з інтервалу на список дат і додали
вимикач `НеУдалятьДокументыКоторыхНетВВыписке` (у стандарті його немає).

Механізм коректний для файлу, який повний за визначенням, і небезпечний для API, де відповідь
обривається непомітно: персональне віддає максимум 500 записів без ознаки продовження, corp за
замовчуванням **10**, будь-який запит може впасти на 429.

Регламент (`СМП_РаботаСБанкамиСервер/Ext/Module.bsl:65-75`) вимикач **не встановлює** — отже
синхронізація увімкнена завжди, незалежно від того, чи виписка доїхала.

### 2.5 Автоматичний обмін для монобанку не працює

`СМП_РаботаСБанкамиСервер.ОбменСБанком` (`Module.bsl:77-83`) має гілки ПриватБанку, ПУМБ і
NovaPay — **монобанку немає**. Форма при цьому показує налаштування розкладу і для монобанку
(`Catalogs/СМП_УчетныеЗаписиБанков/Forms/ФормаЭлемента/Ext/Form/Module.bsl:241`). Та сама
процедура стоїть за кнопкою «Виконати обмін», тож обидва шляхи мовчки нічого не роблять.

Вебхук встановлюється (`Form/Module.bsl:321`), але HTTP-сервісу-приймача в розширенні немає.
У corp API вебхука немає взагалі, тому напрямок — опитування за розкладом.

## 3. Рішення: два незалежні модулі

Транспорти реалізуються окремими модулями, за усталеним у підсистемі патерном «модуль на банк».
Спільного ядра між ними не заводимо.

Підстава — виміряно на чинному коді: наш **мапінг полів** монобанку і ПриватБанку збігається на
**5%** (і то лише `Возврат;`, `Иначе`, `КонецЕсли;`), тобто змістовно не збігається взагалі.
Натомість **обв'язка з формою** збігається на **53%** (55 зі 102 значущих рядків) — але це
дублювання вже існує в усіх чотирьох банківських модулях, а функції курсора
`ЗаписатьЗначениеСведения` / `ПолучитьЗначениеСведения` у ПриватБанку та NovaPay побайтово
ідентичні.

Тобто шов дублювання проходить не між двома монобанками, а поперек усіх банків. Виносити
спільне в межах монобанку означало б зробити один банк несхожим на решту, не прибравши
дублювання ніде. Це окремий борг — див. §10.

## 4. Зміни метаданих

| Об'єкт | Зміна | Навіщо |
|---|---|---|
| `Перечисления.СМП_ПоддерживаемыеИнтеграцииСБанками` | нове значення `МОНОБанкЮр`, синонім «monobank (юрособи)» | маршрутизація режимів через `ФункционалБанкаПодключен` |
| `CommonModules.СМП_РаботаСБанкамиМонобанкЮрAPIСервер` | новий | транспорт ТОВ |
| `Documents.ПоступлениеНаСчет`, `Documents.РасходСоСчета` | новий реквізит `СМП_ИДТранзакцииБанка` — рядок 50, індексований | дедуплікація; 36 символів UUID плюс запас |
| `РегистрыСведений.СМП_НомерПоследнейТранзакции` | ресурс `ИДТранзакции`: 20 → 50 | UUID не влазить у 20 |
| `Справочники.СМП_УчетныеЗаписиБанков` | реквізит `ИД` — починає використовуватись для монобанку | кеш ідентифікатора рахунку |

Розширити `НомерВходящегоДокумента` не можна — розширення 1С не дозволяють змінювати тип і
довжину запозичених реквізитів. Тому власний реквізит.

Подовження ресурсу регістру безпечне для наявних записів ПриватБанку й NovaPay.

Реквізит `СМП_ИДТранзакцииБанка` заповнюється і використовується для пошуку **лише в
монобанківських режимах**. Для решти банків лишається порожнім і поведінки не змінює;
підключення інших банків — окрема правка, свідомо винесена за межі цієї задачі, щоб не чіпати
чотири працюючі інтеграції в одному PR із новим транспортом.

## 5. ФОП-режим: правки на місці

Модуль `СМП_РаботаСБанкамиМонобанкAPIСервер` лишається, змінюється всередині.

| Що | Як |
|---|---|
| Призначення платежу | склейка `description` + `comment`, обидва непорожні, через перенос рядка; межа колонки 255 символів — обрізання з кінця |
| Комісія й кешбек | **лишаються** в призначенні, як зараз (`Module.bsl:330-339`) — єдине джерело для постобробки бухгалтером |
| `hold` | транзакції з `hold = Істина` не вантажаться |
| UTC | `ДатаВремяВUnixTime` переходить на `УниверсальноеВремя()` (`Module.bsl:265`) |
| Пагінація | цикл зі зсувом `to` до часу останньої транзакції, доки сторінка приходить повна (500) |
| Межа періоду | 31 доба + 1 година (2 682 000 с) — ширший період ріжеться на відрізки |
| Помилки | читаємо `errorDescription`, розрізняємо 429 і 404; прибираємо оманливе «некоректний IBAN» (`Module.bsl:181-189`) |
| Ідентифікатор рахунку | кешується в реквізиті `ИД`; `client-info` — лише коли кеш порожній |
| `СМП_ИДТранзакцииБанка` | `id` транзакції повним рядком |

Ліміт персонального API — 1 запит на 60 секунд на кожну функцію; між сторінками витримується
пауза.

## 6. ТОВ-режим: новий модуль

`СМП_РаботаСБанкамиМонобанкЮрAPIСервер`, хост `corp-api.monobank.ua`.

| Що | Як |
|---|---|
| Виписка | `GET /ext/v1/statement/{IBAN}/{from}/{to}?limit=500` |
| `limit` | **передається завжди** — за замовчуванням банк віддає лише 10 |
| Заголовки | `x-token` + обов'язковий `accept: application/json` |
| Рахунок | IBAN напряму, `client-info` не потрібен |
| Що вантажимо | **лише `status = DONE`**; `PENDING` пропускається, `DECLINED` і `reverse` в облік не йдуть |
| Дата документа | `completedTime` (час проведення), не `time` (час створення) |
| Призначення платежу | `description` як є — це вже «Призначення операції» |
| Контрагент | `counterName`, `counterIban`, `counterEdrpou` |
| Фактичний платник | `ultimateDebit` (`name` + `idCode`) дописується в призначення платежу |
| Валюта | `currencyCode` — **рядок**, на відміну від персонального API |
| Пагінація | зсув `to` при повній сторінці |
| Ліміти | читаємо `x-rate-limit-remaining`; при вичерпанні пауза за `x-rate-Limit-retry-after-seconds` |
| `СМП_ИДТранзакцииБанка` | `id` транзакції (UUID) |

Пастка одиниць: у транзакціях суми в копійках, а `Account.balance` — **в одиницях валюти**
(`42.00`). Стосується §7.

Sandbox для цього API не існує — перевірка лише на живому рахунку ТОВ.

## 7. Синхронізація-видалення: нова модель

| Режим | Коли дозволено позначати документи на видалення |
|---|---|
| **ТОВ** | дата має `isFinal = true` **і** виписка витягнута повністю |
| **ФОП** | **ніколи** |

`isFinal` повертає `GET /ext/v1/accounts/{iban}/balances` — прапорець фінальності балансу на
дату. Зі специфікації: «`true` — баланс є остаточним, всі операції за цей день проведені,
подальші зміни неможливі».

Це саме та гарантія, якої бракує стандартному механізму. Але сама по собі вона недостатня:
`isFinal` каже, що день закритий **у банку**, і нічого не каже про те, чи всі його операції
доїхали до нас. Якщо пагінація обірвалась на 429 — день закритий, дані неповні, синхронізація
видалить різницю. Тому транспорт повертає ознаку повноти: **усі запити дали 200 і остання
сторінка неповна**. Синхронізація вмикається лише за збігу обох умов.

Для ФОП `isFinal` в API немає, тому синхронізація не вмикається взагалі. Захист від дублів там
забезпечує реквізит із §4 — саме тому дедуплікація є умовою вимкнення синхронізації, а не
самостійним покращенням.

Технічно це означає, що регламент почне свідомо встановлювати
`НеУдалятьДокументыКоторыхНетВВыписке`, який досі не встановлював ніколи.

## 8. Курсор і регламент

`СМП_РаботаСБанкамиСервер.ОбменСБанком` отримує гілки для обох монобанківських режимів.

Період береться не «поточний день» (`Module.bsl:72-73`), а від курсора в
`РегистрыСведений.СМП_НомерПоследнейТранзакции` — за зразком ПриватБанку
(`СМП_РаботаСБанкамиПриватБанкAPIСервер/Ext/Module.bsl:16-26`, запис на `:485`).

Правило просування курсора: на час останньої **завантаженої** транзакції, але **не далі за
найранішу пропущену** `hold` / `PENDING`. Інакше зарезервована операція, ставши проведеною,
опиниться позаду курсора і не буде запитана ніколи — фільтр §5/§6 перетворився б на тиху
втрату платежу.

Перший запуск без курсора — період із форми.

## 9. Ризики

| Ризик | Пом'якшення |
|---|---|
| Немає sandbox для API юросіб | перевірка на живому рахунку ТОВ, спершу читання за короткий період |
| Довжина `id` персонального API не гарантована банком | реквізит 50 символів із запасом; обрізання не застосовується |
| Зміна довжини ресурсу регістру зачіпає ПриватБанк і NovaPay | подовження рядка сумісне з наявними даними; окремо перевірити після оновлення |
| `isFinal` — молодий механізм, поведінка не перевірена в бою | подвійна умова з ознакою повноти; за сумніву синхронізація не вмикається |
| Новий реквізит у запозичених документах | заповнюється лише монобанківськими режимами, для решти порожній |

## 10. Поза обсягом

- **SMBru і ACC.** SMBru відстає на два виправлення (немає `МестноеВремя`, не заповнюються
  `НомерДок`/`Номер` — тобто дедуплікації там немає в принципі). ACC монобанку не має взагалі,
  його значення переліку підписане «в розробці». Переносимо після обкатки на SMB.
- **Винесення спільної обв'язки** з чотирьох банківських модулів (53% дублювання) і спільних
  функцій курсора (побайтово ідентичні в ПриватБанку й NovaPay) — окрема задача рефакторингу з
  іншим профілем ризику.
- **Дедуплікація для решти банків** — реквізит додається один раз, підключення ПриватБанку,
  ПУМБ, NovaPay і файлових обробок робиться окремо.
- **Вивантаження платіжок** через `/ext/v1/payment/prepare`. Технічно доступне для ТОВ, але
  платіжки «підуть у роботу тільки коли власник в додатку їх підтвердить», тож це окремий
  сценарій із власним UX.
- **Вебхук.** У corp API його немає, у персональному він потребує HTTP-сервісу-приймача, якого
  в розширенні немає. Напрямок — опитування за розкладом (§8).
- **Open Banking** (`ob.mono.bank`) — контур для фінустанов із ліцензією НБУ, вендору облікового
  ПЗ недоступний.
