# Перезапуск SMP_BankExchange як повноцінного 1С-проєкту

**Дата:** 2026-08-28
**Статус:** дизайн затверджено, план реалізації — окремим документом
**Гілка:** `restructure/2026-08` → PR у `main`

## 1. Навіщо

Репозиторій починався як допоміжна копія коду: розширення вивантажувались у форматі EDT і
заливались у git скриптами gitsync. Мета перезапуску — зробити з нього робочий проєкт, у якому
агент (Claude Code + плагін Unica) може розробляти нові інтеграції з банками, виправляти наявні
й проводити рефакторинг, не втративши при цьому історію змін зі сховищ конфігурацій.

Це перший великий проєкт такого роду; підхід має бути придатним до копіювання в інші
репозиторії `SMP_*`, яких очікується більше.

## 2. Що встановила розвідка

### 2.1 Стан репозиторію

118 комітів, 508 файлів, публічний GitHub. Чотири теки верхнього рівня:

| Тека | Зміст | Формат |
|---|---|---|
| `BAS for accounting` | розширення для української бухгалтерії | EDT (`.mdo`, `DT-INF`, Runtime 8.3.22) |
| `BAS small business` | розширення для УНФ UA | EDT |
| `SMB` | розширення для УНФ RU | EDT |
| `ExtDataProcessors` | 12 обробок читання форматів виписок | Designer platform XML + 12 бінарних `.epf` |

Дублювання: ті самі 12 обробок присутні і в `ExtDataProcessors/`, і як `DataProcessors` усередині
UA-розширення. У RU- та ACC-розширеннях їх немає. Коментар до версії сховища фіксує, що всередині
розширення вони «розміщені тимчасово… в подальшому будуть видалені».

### 2.2 Головне обмеження

Unica **не редагує EDT-формат**. Для дерева `.mdo` доступні лише `build`, `syntax edt`,
`extensions`, `test` і читання коду. Операції `meta.*`, `form.*`, `dcs.*`, `role.*`, `cf.*`,
`cfe.*` і `code.patch` оголошені platform-XML-only.

Отже перехід розширень з EDT у Designer platform XML — не покращення, а **умова того, щоб агент
взагалі був корисним** у цьому репозиторії.

### 2.3 Скрипти gitsync непрацездатні

Файл `R:\github\Скрипти запуску gitsync.txt` не запуститься з трьох незалежних причин:

1. **OneScript не встановлений.** Каталог установки відсутній; `oscript`, `opm`, `gitsync` не
   резолвляться (шлях лишився в `PATH` як залишок).
2. **Платформа 8.3.22.1923 відсутня.** Установлені гілки — 8.3.20, 8.3.23, 8.3.24, 8.3.25, 8.3.27.
   Ключ `--v8version 8.3.22.1923` впаде одразу.
3. Останній фактичний запуск — червень 2025 (залишки в теці tempdir).

Шляхи до сховищ та імена розширень у скриптах при цьому лишаються актуальними.

### 2.4 Сховища живі, історія доступна

Перевірено безпосередньо платформою 8.3.27.1644 через тимчасову файлову ІБ (для сховищ — режим
читання). Сервісний користувач сховищ автентифікується.

| Розширення | Версії у сховищі | Період | Залито в git | Не залито |
|---|---|---|---|---|
| `SMP_BankExchange_SMB` (УНФ UA) | 2…47 | 16.03.2024 – 22.01.2026 | 23 | **22 версії** |
| `SMP_BankExchange_ACC` (Бухгалтерія) | 2…44 | 18.05.2021 – 18.02.2025 | 35 | **7 версій** |
| `SMP_BankExchange_SMBru` (УНФ RU) | 5…16 | 02.04.2024 – 06.12.2024 | 15 | **1 версія** |

Разом близько **30 версій сховищ з авторами, датами й коментарями ще не потрапили в git**.
Найбільша прогалина — UA-розширення: майже два роки роботи.

### 2.5 Новий конвеєр перевірено end-to-end

Повний ланцюжок пройдено без gitsync і без OneScript, самою платформою 8.3.27.1644:

```
CREATEINFOBASE
  → LoadCfg <порожній стаб .cfe> -Extension <Ім'я>
  → ConfigurationRepositoryUpdateCfg -v <N> -Extension <Ім'я>
  → DumpConfigToFiles <каталог> -Extension <Ім'я>
```

Результат: 275 файлів Designer XML, `unica.project.map` бачить `sourceFormat: platform_xml`.
Усі кроки — код повернення 0.

Деталі, які варто зафіксувати, бо на них легко втратити час:

- **Порядок аргументів.** `-Extension` належить команді-дії (`/ConfigurationRepositoryReport`,
  `/ConfigurationRepositoryUpdateCfg`, `/DumpConfigToFiles`), а не `/ConfigurationRepositoryF`.
  Без нього платформа відповідає «Соединение основной конфигурации с хранилищем расширений
  конфигураций невозможно».
- **Розширення має існувати в цільовій ІБ до звернення до сховища.** У порожній базі спершу
  `LoadCfg` порожнього стаба `.cfe` з потрібним іменем, інакше — «расширение конфигурации с
  указанным именем не найдено».
- **Кирилиця в шляхах.** `.cmd`-обгортки читаються в OEM-кодуванні; кириличні шляхи треба
  передавати аргументами, а не вшивати в тіло скрипта, інакше сховище «не обнаружено».
- **Звіт сховища — це MXL**, не текст. Метадані версій (номер, автор, дата, час, версія
  конфігурації, коментар) парсяться з текстового представлення MXL і вже успішно вилучені.

## 4. Цільова структура

```
SMP_BankExchange/
├─ BankExchange_SMB/            продукт: УНФ UA (BAS small business)
│  ├─ cfe/src/                  вихідники розширення, Designer XML — у git
│  ├─ cf/                       базова конфігурація — gitignored цілком
│  │  └─ README.md              єдиний закомічений файл: як вивантажити, звідки
│  ├─ v8project.yaml            воркспейс unica: cf(CONFIGURATION) + cfe(EXTENSION)
│  ├─ v8project.local.yaml      gitignored: підключення та логіни
│  ├─ storage.json              сховище, ім'я розширення, остання залита версія
│  ├─ build/                    gitignored
│  └─ README.md
├─ BankExchange_SMBru/          продукт: УНФ RU
├─ BankExchange_ACC/            продукт: БАС Бухгалтерія
├─ epf/                         продукт: 12 обробок читання форматів
│  ├─ src/                      один EXTERNAL_DATA_PROCESSORS-корінь
│  ├─ dist/                     зібрані .epf (доки не вирішено про релізи)
│  ├─ v8project.yaml
│  └─ build/                    gitignored
├─ docs/
│  ├─ architecture/             підсистема, контракт обробки, контур «сховище ↔ git»
│  ├─ banks/                    по банку: формат, API, статус
│  └─ superpowers/specs/
├─ tools/
│  ├─ storage-sync.ps1
│  ├─ dump-config.ps1
│  ├─ load-ext.ps1
│  ├─ build.ps1
│  └─ lib/
├─ AUTHORS
├─ CLAUDE.md
├─ README.md
└─ LICENSE
```

Обґрунтування ключових рішень:

**Продукт у корені, артефакти всередині.** Коли `cf/` і `cfe/` лежать в одному воркспейсі,
`v8project.yaml` описує обидва source-set-и разом. Це та форма, якої вимагає Unica: `config-init`
не працює без `CONFIGURATION`-набору, а `cfe.borrow`, `cfe.diff` і `cfe.validate` без
конфігурації-власника неповноцінні.

**Назва теки = ім'я розширення в 1С мінус префікс `SMP_`.** Поточні назви плутають: `SMB` — це
російська УНФ, а `BAS small business` — українська. Нові збігаються з тим, що видно в
Конфігураторі й у сховищі.

**`cf/` у `.gitignore` цілком, з одним `README.md`.** Це і ліцензійна вимога (вендорський код у
публічному репозиторії неприпустимий), і захист від випадкового коміту: тека фізично існує, але
git бачить у ній лише пояснення.

**Вузький `cwd` для Unica.** Воркспейс — тека продукту, не корінь репозиторію. Автоскан Unica
обходить усе дерево від `cwd` і падає на першому не-UTF-8 файлі; вузький корінь також тримає
BSL-індекс і кеш `.build/unica` малими.

## 5. Контракти файлів

### 5.1 `v8project.yaml` продукту-розширення

```yaml
format: DESIGNER
builder: DESIGNER
workPath: 'build'
execution_timeout: 600000
source-set:
  - name: base
    type: CONFIGURATION
    path: 'cf/src'
  - name: BankExchange_SMB
    type: EXTENSION
    path: 'cfe/src'
```

Підключення до ІБ і логіни — **тільки** у `v8project.local.yaml` поруч (gitignored). Локальний
файл може перевизначати лише `workPath`, `infobase`, `tools`, `tests`, `mcp`.

### 5.2 `v8project.yaml` продукту `epf/`

```yaml
format: DESIGNER
builder: DESIGNER
workPath: 'build'
source-set:
  - name: bank_formats
    type: EXTERNAL_DATA_PROCESSORS
    path: 'src'
```

Пишеться руками: автовиявлення `config-init` відмовляє, якщо в дереві немає
`CONFIGURATION`-набору.

### 5.3 `storage.json`

Замінює gitsync-івський `VERSION`. Тримає конфігурацію синхронізації поруч із тим, що
синхронізується, тому скрипт не потребує аргументів.

```json
{
  "storagePath": "<локальний шлях до каталогу сховища>",
  "extensionName": "SMP_BankExchange_SMB",
  "lastSyncedVersion": 23,
  "sourcePath": "cfe/src"
}
```

Ім'я користувача сховища й підключення живуть у `v8project.local.yaml` (gitignored) — сюди не
потрапляють. Пароля немає взагалі: сервісний користувач сховищ його не має.

### 5.4 `AUTHORS`

Наявний файл gitsync — мапінг «ім'я користувача у сховищі → git-автор» у форматі
`Ім'я=Name <email>`. Перевикористовується новим скриптом; потребує доповнення для авторів, яких
у ньому ще немає.

### 5.5 `.gitignore`

Шаблони пишуться **без провідного слеша**, щоб діяли на всіх рівнях вкладеності:

```
cf/
build/
.build/
v8project.local.yaml
ConfigDumpInfo.xml
DumpFilesIndex.txt
```

## 6. Інструменти

Усі — PowerShell 7, у `tools/`, залежать лише від платформи 1С 8.3.27.x і git.

| Скрипт | Призначення |
|---|---|
| `storage-sync.ps1` | сховище → git: читає звіт сховища, для кожної нової версії оновлює тимчасову ІБ, вивантажує Designer XML і робить коміт з автором, датою й коментарем зі сховища; оновлює `storage.json` |
| `dump-config.ps1` | дев-база → `<продукт>/cf/src`: вивантаження базової конфігурації для повноцінної роботи Unica |
| `load-ext.ps1` | git → дев-база: `/LoadConfigFromFiles -Extension` після злиття гілки |
| `build.ps1` | `src` → `build/`: збірка `.cfe` розширень і `.epf` обробок |
| `lib/` | парсер MXL-звіту сховища, мапінг авторів, обгортки над `1cv8.exe` |

**Захист від розбіжності.** Перед роботою `storage-sync.ps1` порівнює номер версії у сховищі з
`lastSyncedVersion` і зупиняється, якщо git попереду або історії розійшлися. Розбіжність
виявляється до того, як щось буде затерто.

**Збірка `.epf`/`.cfe` — лише платформою.** Операція `make` в Unica на Windows падає на публікації
артефакту (`Отказано в доступе, os error 5`), лишаючи стейдж-файл. Тому `build.ps1` викликає
`DESIGNER /LoadExternalDataProcessorOrReportFromFiles` напряму. Так само напрямок «база → git»
(`dump`) в Unica на Windows fail-closed — його робить Конфігуратор.

## 7. Контур «сховище ↔ git»

Сховище 1С не вміє бути пасивним дзеркалом: воно вимагає захоплення об'єктів, і паралельне
редагування того самого модуля в git і у сховищі дає конфлікт. Тому контур двонаправлений, але
асиметричний:

| Напрямок | Чим | Коли |
|---|---|---|
| сховище → git | `storage-sync.ps1` | автоматично; догоняє все, що команда закомітила у сховище |
| git → база | `load-ext.ps1` | після злиття PR |
| база → сховище | вручну в Конфігураторі або скриптом на явну команду | останній крок; **ніколи автоматично** |

## 8. План міграції

### Етап 0 — страховка

Гілка `restructure/2026-08`; `main` не змінюється до злиття PR. `git bundle` усього репозиторію
як офлайн-бекап. Сховища — тільки читання.

*Критерій приймання:* бандл існує й перевірений `git bundle verify`.

### Етап 1 — реструктуризація, один коміт

`git mv` у фінальні шляхи. Вміст поки лишається EDT; важливо, що шляхи вже кінцеві — наступні
коміти замінять вміст за тими самими шляхами, і `git log --follow` не розірветься на переїзді.

```
BAS small business/*      → BankExchange_SMB/cfe/*
SMB/*                     → BankExchange_SMBru/cfe/*
BAS for accounting/*      → BankExchange_ACC/cfe/*
ExtDataProcessors/*/src/* → epf/src/*
ExtDataProcessors/*/*.epf → epf/dist/*.epf
```

Плюс `.gitignore` і каркас `docs/`. `CLAUDE.md` та `.claude/settings.json` написані ще на етапі
проєктування, щоб виконавець плану вже мав контекст і межі.

*Критерій приймання:* `git status` чистий; `git log --follow` на довільному BSL-файлі показує
історію до переїзду.

### Етап 2 — догнати історію

По одному коміту на версію сховища. Перший коміт кожного продукту заразом видаляє EDT-дерево й
кладе Designer XML: формат ламається один раз, у місці, де він реально змінився.

Порядок — від найменшого обсягу до найбільшого, щоб проблеми виявились дешево:

| Продукт | Версії | Комітів |
|---|---|---|
| `BankExchange_SMBru` | 16 | 1 |
| `BankExchange_ACC` | 36 → 44 | 7 |
| `BankExchange_SMB` | 24 → 47 | 22 |

*Критерій приймання:* `storage.json` кожного продукту вказує на максимальну версію сховища;
автор, дата й коментар кожного коміту збігаються зі звітом сховища; повторний запуск
`storage-sync.ps1` не створює комітів.

### Етап 3 — контур Unica

Чотири `v8project.yaml`, три `storage.json`, `v8project.local.yaml` з підключеннями.

*Критерій приймання:* на кожному продукті `unica.project.map` показує `platform_xml` і правильні
типи source-set-ів; `unica.cfe.validate` проходить; `unica.code.diagnostics` дає базовий зріз по
BSL без падінь.

### Етап 4 — документація

`docs/architecture/`: як влаштована підсистема, контракт обробки читання формату, контур сховищ.
`docs/banks/`: по банку — формат, API, статус. `CLAUDE.md`: шляхи, бази, межі, чого не робити.

*Критерій приймання:* нова сесія агента здатна за `CLAUDE.md` і `docs/architecture/` дійти до
робочої операції без розвідки файлової системи.

### Етап 5 — поза цим перезапуском

Видалення 12 обробок з UA-розширення. Це зміна прикладної логіки, а не інфраструктури: спершу
потрібна перевірка, чи немає в коді розширення прямих звернень до внутрішніх
`Обработки.СМП_ОбработкаВыпискиБанка_*`, і зміну доведеться заносити у сховище. Окрема задача
після того, як контур запрацює.

| Ризик | Пом'якшення |

артефактів і GitHub Releases; видалення дубльованих обробок з UA-розширення; CI.

## 10. Довідник оточення

Конкретні рядки підключення, імена серверів, логіни та шляхи до сховищ **навмисно не наведені**:
репозиторій публічний. Вони зберігаються у:

- `<продукт>/v8project.local.yaml` — підключення до дев-бази (gitignored);
- `<продукт>/storage.json` — шлях до сховища й ім'я розширення (закомічено; шлях локальний, паролів немає);
- пам'яті проєкту агента — зведена мапа «продукт → розширення → сховище → дев-база».

Платформа: гілка **8.3.27.x** (Unica підтримує тільки її). Сховища створені тією ж версією.
