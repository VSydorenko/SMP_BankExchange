### 0.1. Нинішня форма і транзакція запису (читання коду)

- Запис документа **не** загорнутий у `НачатьТранзакцию` ні в основному шляху, ні в запасному, ні в
  шляху одного рядка. Повним пошуком `НачатьТранзакцию|ЗафиксироватьТранзакцию|ОтменитьТранзакцию` по
  всіх `.bsl` обробки `СМП_КлиентБанк` знайдено 3 збіги, усі в одному файлі: `ManagerModule.bsl`,
  функція `СоздатьКонтрагентаПоСтруктуреДанных`. Транзакція там охоплює лише створення контрагента,
  договору й рахунку. Документ пишеться в `ЗаписатьОбъект` у `Попытка` без транзакції.
- Основний шлях — тривала операція БСП. Форма (`ДлительнаяОперацияЗагрузкиВыписки`, сервер) викликає
  `ДлительныеОперации.ВыполнитьФункцию(..., "Обработки.СМП_КлиентБанк.Загрузить", КонтекстФормы)`, далі
  `Загрузить` → `ЗагрузитьСтроку` → `ЗаписатьОбъект` модуля менеджера.
- Один рядок («Завантажити поточний платіж») йде прямим серверним викликом, без тривалої операції й
  без транзакції: `ЗагрузитьТекущийПлатежНаСервере` → `ObjectModule.ЗагрузитьОднуСтроку`.
- Висновок для задачі 7: шаблон «тривала операція з функцією модуля менеджера обробки розширення»
  у цій базі робочий. Запис поза транзакцією — та сама умова, що й у `records.md` §2.

### 0.2. Тривала операція БСП: користувач, мова, транзакція (зонд)

Виклик `ДлительныеОперации.ВыполнитьФункцию` з функцією серверного модуля розширення тестів,
`ОжидатьЗавершение = 60`. Результат:

| Що | Прогноз (план) | Виміряно |
|---|---|---|
| завдання справді фонове | — | `Статус=Выполнено`, у фоні `ПолучитьФоновоеЗадание() <> Неопределено` — так; у викликача — ні |
| (а) користувач | той, хто запустив | `ИмяПользователя()` і `Пользователи.ТекущийПользователь()` збігаються з викликачем — **підтверджено** |
| (б) мова | мова користувача | `ТекущийЯзык()` і `НСтр` у фоні такі самі, як у викликача: `ru`/`RU` — **підтверджено для сеансу `ru`**; сеанс `uk` не міряно → чек-лист власника |
| (в) транзакція у фоні | поза транзакцією | `ТранзакцияАктивна()` у фоні — Ложь — **підтверджено**; режим «не у фоні» (файлова база) на серверній базі не відтворюється, не міряно |

Наслідок для архітектури форми: `Ответственный` однаково передається параметром, як записано в плані.
Збіг користувача — факт, а не причина відмовитися від явної передачі.

### 0.3. Запис проведеного документа (зонд)

Документ — `ПоступлениеНаСчет`, створений і проведений продуктом (`СМП_ЗаписьДокументовБанка.Записать`
через помічники `СМП_ТестыЗаписиКаркас`). Змінено реквізит `Комментарий`. Рухи рахувались по
`РегистрНакопления.ДенежныеСредства`.

| Режим | Прогноз (план) | Виміряно |
|---|---|---|
| (а) `Записать(РежимЗаписиДокумента.Запись)` | відмова платформи | **СПРОСТОВАНО.** Винятку немає; документ лишається **проведеним**, рухів до 2, після 2. Дані змінено, а старі рухи лишились, і проведення їх не перерахувало |
| (б) `Записать(РежимЗаписиДокумента.ОтменаПроведения)` | записаний непроведеним, рухів немає | **Підтверджено**: винятку немає, `Проведен` — Ложь, рухів 0 |

**Наслідок для задачі 6.** Перезапис проведеного документа не може писатися режимом `Запись`: дані
документа й рухи розійшлися б мовчки. Правильний порядок: перезапис записується з
`ОтменаПроведения`, потім іде спроба провести, як для нового документа (D20). Якщо проведення не
вийшло, документ лишається записаним непроведеним без старих рухів. Саме про це попереджає форма
(А1.6). Що лишається в базі при відмові проведення **поза** транзакцією — не міряно (гіпотеза
журналу 04, адресат — план 4б).

### 0.5. Оповіщення списків «Банк і каса» (читання коду `cf/src`)

- `БанкИКасса.ФормаСписка.ОбработкаОповещения`:
  - `"ОповещениеОбИзмененииДолга"` → оновлення **підсумків** (за варіантом показу), без `Обновить()`
    списку;
  - `"Запись_ПоступлениеНаСчет"`, `"Запись_РасходСоСчета"` (та інші `Запись_*`) з `Параметр.Ссылка` —
    лише позиціонування поточного рядка.
- Форми списків `ПоступлениеНаСчет`, `РасходСоСчета` і журналу `ДокументыПоБанку` обробляють лише
  свої `Запись_*` (поточний рядок).
- Список виписок журналу — динамічний, основна таблиця `DocumentJournal.ДокументыПоБанкуИКассе`,
  `AutoRefresh = false`. Явного `Обновить()` від подій у коді немає.
- Форми документів вендора після запису кличуть `Оповестить("Запись_<Документ>", ..., Ссылка)`,
  `Оповестить("ОповещениеОбИзмененииДолга")` і, для оплати рахунку, `ОповеститьОбИзменении(Тип(...))`
  рахунків.
- Прогноз плану: «`ОповещениеОбИзмененииДолга` оновлює підсумки» — **підтверджено** кодом.
  «`ОповеститьОбИзменении(Тип(...))` оновлює динамічні списки, зокрема журнал» — **не міряно**. Це
  платформна поведінка, у коді вендора її не видно, і зонд у клієнті агенту недоступний.
- **Вхід задачі 7** (на рішення планувальника на контрольній точці): після запису форма робить те,
  що робить форма документа вендора, — `ОповеститьОбИзменении` за типами `ПоступлениеНаСчет` і
  `РасходСоСчета` та `Оповестить("ОповещениеОбИзмененииДолга")`. Чи оновлюється відкритий журнал
  «Банк і каса», перевіряє власник у дев-базі (критерій D10). Якщо ні, запасний варіант —
  `Оповестить("Запись_<Документ>", , Ссылка)` останнього документа. Він теж не оновлює список, лише
  ставить рядок, тож тоді потрібне окреме рішення.

спільної бази й ширше за цю умову не поширюється.

**Бриф:** план `4b03d00` + скорочення (постійний лише Т1 з двох кейсів інваріанта безпеки; мутації — лише для них).

(ключ у типах рішень, сигнатура та сама; лише одне в виклику): `Истина` — рядок скидається до фактів банку + документ і
версія, проганяється кроками як новий; `Ложь` — стан кроку 0 (вид, контрагент, договір з документа). Відмови: без

(захисна); документа немає → `Ошибка`; позначений на видалення → `УжеЗагружен`; версія змінилась → `УжеЗагружен`
