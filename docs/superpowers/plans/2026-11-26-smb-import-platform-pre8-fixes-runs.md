### 2. Номери рахунків організацій для рішення 1

Готової функції, що годиться як є, **немає**. Найближча — `СМП_РаспознаваниеОпераций.ПрочитатьСчетаОрганизацийИФизлиц(Номера)` (приватна, `Функция`):
- запит до `Справочник.БанковскиеСчета` `ГДЕ НЕ ПометкаУдаления И (Владелец ССЫЛКА Организации ИЛИ ФизическиеЛица) И (НомерСчета В (&Номера) ИЛИ НомерСчетаУстаревший В (&Номера))`;
  повертає масив структур `Ссылка, Номер (нормалізований поточний), Устаревший (нормалізований застарілий), Владелец, ВладелецНаименование, КонтрагентИнтеркампани`, порядок за кодом;
- `НормализованныйНомерСчета(Номер)` — `СМП_ВыпискаБанка`, **експортна** (без пробілів, верхній регістр); розпізнавання нормалізує нею і поточний, і застарілий номер рахунку;
- кличе її лише `ШагСвойСчетИСотрудник` (один запит на конверт): збирає `Номера` — для кожної операції нормалізований номер **і** `ВРег(СокрЛП(сирий))`, далі `НайтиСвойСчетСтроки(Элемент.Номер, Счета)`.
Розбіжності з рішенням 1 (тому потрібна **нова функція**, спільна для розпізнавання й запису — місце за планом задачі 1):
1. виключає помічені на видалення (рішення 1 їх включає); 2. включає фізосіб (рішення 1 — лише власник-організація); 3. відбір за переданим списком сирих варіантів
   (`В (&Номера)`): номер, що в базі лежить з пробілами/в нижньому регістрі, **не знайдеться** варіантами «нормалізований / ВРег(СокрЛП)» — для множини організацій безпечніше читати
   **всі** рахунки з власником-організацією без відбору за номером (їх мало) і нормалізувати в BSL тією ж `НормализованныйНомерСчета`; 4. результат — масив структур на рахунок, а запису потрібна множина номерів
   (Соответствие нормалізований номер → власник/ознака) на один `Записать`.
Висновок: додати одну функцію «множина номерів рахунків організацій (поточний і застарілий, включно з поміченими)» і викликати з `ПричинаОтказаСтроки` (гілка без ідентифікатора) та, за бажанням, з
розпізнавання; `ПрочитатьСчетаОрганизацийИФизлиц` лишити для кроку «свій рахунок / співробітник». Метаданих не потребує.

### 3. `Прочее` обох напрямів: запис і перевірка заповнення вендора (без контрагента й рахунку контрагента)

- **Запис плану** (`СМП_ЗаписьДокументовБанка`): `ПричинаОтказаСтроки` вид `Прочее` не відхиляє (контрагента, рахунку контрагента, статті не вимагає). `ЗаполнитьДокументПоСтрокеПлана`: контрагент
  ставиться лише для видів з контрагентом — `ВидыОперацийСКонтрагентом()` (ОтПокупателя, ОтПоставщика, ОтНашейОрганизации, оплата/повернення карт і кредитів, РасчетыПоКредитам, Поставщику, Покупателю,
  НашейОрганизации, КомиссияБанка, ПрочиеРасчеты) — **`Прочее` у переліку немає**; `СчетКонтрагента` ставиться лише з контрагентом або для видів переказу (`ЭтоВидПеревода`) — для `Прочее` ні;
  рядка розшифрування платежу немає (тільки для `ПрочиеРасчеты`, видів з договором, або від основи); `Корреспонденция` — з плану, а за видом лише `ЛичныеСредстваПредпринимателя` (`НераспределеннаяПрибыль`) і
  `КомиссияБанка` (`ПрочиеРасходы`): для `Прочее` порожня, якщо її не дали платіжне доручення / правило / людина; стаття — з плану, інакше вендорська `ПолучитьДанныеСтатьиДДС` за видом
  (`Прочее` → стаття `Прочее`, `СтатьяДДСПоВидуОперации`; **стаття ДДС для проходження перевірки окремо не потрібна**).
- **`ОбработкаПроверкиЗаполнения` вендора** (`base:Document.ПоступлениеНаСчет` і `…РасходСоСчета`, `locked`):
  - `ПоступлениеНаСчет.Прочее`: знімає `Контрагент`, `Подотчетник`, `Документ`, `Курс`, `Кратность`, `СуммаУчета`, `РасшифровкаПлатежа(+колонки)`, `ВидНалога`, `ПодразделениеЗатраты`, еквайринг, договори; **`Корреспонденция` НЕ знімає** — обов'язкова;
    рахунок контрагента не перевіряється взагалі.
  - `РасходСоСчета.Прочее`: знімає `Контрагент`, `Подотчетник`, `ВидНалога`, `РасшифровкаПлатежа(+колонки)`, еквайринг, `Подразделение` (лише якщо `Корреспонденция.ТипСчета <> Расходы`), `ПериодРегистрации`;
    **`Корреспонденция` НЕ знімає**; рахунок контрагента не перевіряється.
  - Тобто контрагент і рахунок контрагента для `Прочее` обох напрямів перевірку **проходять**; єдиний обов'язковий реквізит, якого план за рішенням 2 не дає, — `Корреспонденция`
    (для `Расход` при типі рахунку «Расходы» — ще `Подразделение`, яке запис ставить за правилом/підрозділом відповідального).
- **Наслідок для рішення 2 (розбіжність, що не міняє рішення, але міняє очікування):** рядок `Прочее` без кореспонденції запис створить, але **непроведеним** з причиною від вендора (зауваження `Ошибка`, сусіди пакета пишуться й
  проводяться) — виміряно раніше (журнал плану 04, «Таблиця видів» і тест «дані плану відсутні → непроведений з причиною»: «`Прочее`/`НаРасходы` без кореспонденції» → «записаний непроведеним, причина названа зауваженням `Ошибка`»; сам тест у поточному `tests/src` за цим іменем не знайдено — стан міг змінитись планом simplify; `Прочее`
  з кореспонденцією з плану → «Создан», без контрагента). Для 8 операцій 4б (комісія, купівля валюти, внесення готівки) після рішення 2 це означає: «Перевірте операцію» + непроведений документ, поки кореспонденцію не
  дасть правило (D24, поза блоком) або людина. Спека (D25 крок 1) цього не обіцяє інакше («Перевірте операцію»). **Питання архітектору (не блокує):** чи це прийнятно, чи рішення 2 мусить
  ще й ставити `Корреспонденция` (`ПрочиеРасходы`/`ПрочиеДоходы` — гілка вендора з вимкненою опцією «ОтображатьСчетаУчета» свідомо не переносилась, у виміряній базі опція ввімкнена). Прямий прогін вендорської

### 5. Діагностики рівня `Ошибка` конекторів прийнятого конверта

Конектор пише їх через `СМП_КоннекторыБанковОбщее.ДобавитьДиагностику(Выписка, "Ошибка", Номер, Текст)`; колонки діагностики — лише `Уровень`, `ПорядковыйНомер` (номер **запису** джерела, не рядка операції — операції в конверті немає),
`Текст`. Дати/суми/напряму діагностика зараз не несе (`ПроверитьВыписку` лише копіює її й ставить `ЕстьНевалидныеСтроки`; конвеєр її не читає — див. п. 1). Колонка «дата в точці» — чи **конектор у цій точці вже знає** дату (так → кандидат на позначку доби за умовою додатку; ні → курсор правилом не тримається).

| Конектор | Умова → текст (коротко) | Дата в точці |
|---|---|---|
| **monobank юросіб** (`ОбработатьЗаписи`) | запис не об'єкт JSON | ні |
| | `time`/`completedTime` не читається | ні |
| | `status` не PENDING/DECLINED/DONE → «неизвестное состояние» | так (`Создана`) |
| | `reverse` з `id` остаточного оригінала в тому ж читанні → «повторяет идентификатор исходной операции…» (випадок (б)) | так (`Создана`; сума/напрям — з оригіналу) |
| | `amount` не число | так |
