## Мета й межі

Три виправлення, без яких етап 8 дав би хибні дані без сигналу: (А) Р4б-1; (Б) ОТП 660; (В) реверс monobank (б). Поза межами: етап 8,
NovaPay, нові читачі, комісія з типовими правилами (D24), договори (D15).

## Виміри (повністю — журнал блоку, «Виміри до плану»)

- **(А)** Розпізнавання для «рахунок кореспондента = рахунок виписки» лише попереджає, далі ставить `ДействиеСчет = Создать`; запис
  створює рахунок без перевірки номера. У 4б таких операцій **8** (6 списань, 2 надходження: комісія, купівля валюти, внесення готівки).
  Вендор для вихідного платежу на свій рахунок ставить `Прочее` і рахунку контрагента не створює. Спека цього випадку не описує.
- **(Б)** Перевірка ОТП відкидає 660 на довжині першого рядка з текстом про довжину; ознака 660 — довжина 660, `0`/`1` на 115, цифри на
  655–660; знеособлений макет 660 є в тестовому розширенні.
- **(В)** Реверс (б) юросіб — діагностика `Ошибка` без операції й без дати; регламент її не бачить → «Успех», курсор далі, позначки немає:
  повернення втрачено мовчки. Реверсу в run1/run3 немає, синтетика — mono-corp `СинтСтатусы`.

## Рішення

1. **Інваріант (А):** рахунок контрагента з номером рахунку організації — постійна відмова рядка. Одне місце — `ПричинаОтказаСтроки`,
   гілка без ідентифікатора (прохід 2 не створює ні контрагента, ні рахунку); перевіряється і номер, що створюється, і остаточний
   `СчетКонтрагента` (зокрема хибний, створений до виправлення). Множина номерів — один запит на `Записать`: нормалізований номер,
   поточний і застарілий, включно з поміченими на видалення, власник — організація; спільна з розпізнаванням функція.
   `ПостоянныйОтказСтрокиПлана` бачить ту саму причину; `СоздатьСчетГруппы` без змін.
2. **Вид для «рахунок кореспондента = рахунок виписки»** (Р-1 A): `ПрименитьПереводМеждуСвоимиСчетами` скидає контрагента й рахунок
   (`НеТребуется`), вид `Прочее` обох напрямів, «Перевірте операцію» з наявним попередженням.
3. **(Б):** у `ПричинаНеПохожНаФормат` перед перевіркою довжини — гілка «рядок рівно 660 **і** `0`/`1` на 115 **і** цифри на 655–660» →
   uk «Файл ОТП Банку старого формату (покоління 660) — вивантажте виписку в новому форматі.», ru — той самий зміст. Обгортка без змін.
4. **(В)** (Р-2 A): реверс (б) — постійна відмова з позначкою. Механізм — **додавання до контракту** (версіонування колонок
   `reader-contract.md`): необов'язкові `Дата`, `Сумма`, `Направление` у `Диагностика` (юросіб заповнює для (б) з оригінала);
   `ПроверитьВыписку` для `Ошибка` з датою додає рядок `НевалидныеСтроки` з необов'язковим `Текст`; `ОтметкиОтказов` бере `Текст`, якщо є.
   Текст: «повернення операції <дата, сума>: банк змінив стан переданої операції, документа повернення немає — внесіть повернення формою
   або файлом виписки». Курсор не тримає, «дія людини».
5. `reader-contract.md` («Ознака для курсора», «Діагностика») — до коду й рішення 4.

**Наявні хибні рахунки й документи не чіпаємо:** задача 0 рахує їх у базі агента, рішення 1 не дає їх використати, сценарій власника
дає запит, як їх знайти; рішення — за власником.

Не змінюються: сигнатури читачів і точки читання (лише додавання), стан і курсор 5б, D17.

## Розвилки (до прийняття плану)

- **Р-1 (рішення 2).** A — `Прочее` обох напрямів без контрагента й рахунку (як вендор); B — `ДействиеСчет = НеСоздавать`, вид
  `Поставщику`/`ОтПокупателя` (контрагент-банк без рахунку); C — лише правило комісії (D24, поза блоком) + рішення 1. Рекомендація **A**.
- **Р-2 (рішення 4).** A — (б) постійна відмова з позначкою; B — (б) тримає курсор (регламент рахунку стоїть, доки людина не внесе
  повернення й не зніме позначку); C — лишити, задокументувати. Рекомендація **A** (D18 п. 1: позначка замість мовчазної втрати, без
  зупинки). **Ширше питання:** будь-яка діагностика `Ошибка` прийнятого конверта регламенту не видна — правило рішення 4 механізмом
  загальне (дата → позначка), але в цьому блоці його заповнює лише (б); перелік інших `Ошибка` конекторів — вимір задачі 0, загальне
  правило — рядок у дорожню карту. Рішення 4 — **додавання до контракту читача**: якщо архітектор вважає це поза блоком, лишається B або C.
- **Тести понад бриф:** бриф дає задачі (А) один keep-тест; план — один тест із двома сценаріями (рішення 1 і 2) і окремий тест (б) у
  `СМП_ТестыКонвейера` (інваріант втрати даних). Потрібне «так» архітектора.
