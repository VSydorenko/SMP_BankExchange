# Контракт читача виписок

Документ для розробника, який пише власну зовнішню обробку-читач банківської виписки. Щоб
написати читач, код розширення читати не потрібно: усе, на що читач може спиратися, описано тут.
Старий контракт обробок (`Загрузить_УНФ`) описано в `data-processor-contract.md`; він чинний для
старої обробки до перемикання на нову платформу, а нова платформа його не підтримує.

Контракт однаковий для вбудованих читачів файлів, конекторів API і зовнішніх обробок, а також
для всіх трьох конфігурацій (УНФ українська, УНФ російська, бухгалтерія). Тому він спирається
лише на типи платформи 1С і не згадує об'єктів конфігурації: та сама `.epf` працює скрізь.

## Принцип

Читач **лише читає вхід і заповнює конверт**, який йому надає платформа. Він не створює
документів, не шукає контрагентів, не рахує ключ дедуплікації, не знає модулів розширення.
Усе, що залежить від конфігурації (розпізнавання, запис документів), робить платформа. Читач
описує факти банку: що, коли, скільки, між якими рахунками.

Звідси кілька наслідків:

- конверт створює платформа; читач не підміняє його власним об'єктом;
- схему конверта задає один конструктор у розширенні, і платформа порівнює з ним усе, що
  повернув читач; читач не додає й не вилучає колонок;
- невалідний рядок не завантажується, але й не зникає мовчки: він потрапляє в діагностику
  (жодна банківська операція не пропускається непомітно).

Платформа на межі звіряє рівно таке:

- тотожність конверта (це той самий об'єкт, який створила платформа);
- `ВерсияКонтракта`;
- схеми таблиць `Операции` і `Диагностика` (набір колонок, їхні типи й уточнення);
- правила окремого рядка операції (розділ «Що платформа робить з конвертом»);
- рівні повідомлень діагностики читача.

Скалярні поля самого конверта в контракті версії 1 **не перевіряються**: `НачалоПериода`,
`КонецПериода`, `НачальныйОстаток`, `КонечныйОстаток`, `ЧтениеПолное`, `ГраницаДоверия`
платформа приймає такими, як їх залишив читач. Відповідальність за їхній зміст лежить на читачі.

## Дві функції читача

Обробка експортує дві функції.

### `ОписаниеЧитателя()`

Без параметрів. Повертає структуру з полями:

| Поле | Тип | Зміст |
|---|---|---|
| `Идентификатор` | Строка | Непорожній ідентифікатор читача |
| `ВерсияКонтракта` | Число | Ціле; версія контракту, за якою працює читач (поточна — 1) |
| `Наименование` | Строка | Назва читача для адміністратора |
| `РасширенияФайлов` | Массив из Строка | Розширення файлів, які читач вміє читати: без крапки, без пробілів, у нижньому регістрі; порожній масив — читач API |
| `ДаетИдентификаторыОпераций` | Булево | Чи заповнює читач `ИдентификаторОперации` |
| `ДаетОстатки` | Булево | Чи заповнює читач початковий і кінцевий залишки |

Платформа перевіряє опис, не кидаючи виняток: кожне порушення — окремий зрозумілий текст для
адміністратора (відсутнє поле, неправильний тип, непідтримувана версія, недопустиме розширення).
Відсутність функції або непідтримувана версія контракту дають адміністратору повідомлення, а не
мовчазну відмову.

### `Прочитать(Данные, Параметры, Выписка)`

| Параметр | Тип | Зміст |
|---|---|---|
| `Данные` | ДвоичныеДанные | Вміст виписки |
| `Параметры` | Структура | Параметри читання (нижче) |
| `Выписка` | Структура | Порожній конверт, створений платформою; читач його заповнює |

Результату функція не повертає: все, що читач має передати, лежить у `Выписка`.

Якщо читачеві потрібен тимчасовий файл (формати DBF, XML), він створює його **сам і з унікальним
іменем** — паралельні завантаження не повинні перетиратись. Видалити файл теж обов'язок читача.

**Параметри читання:**

| Поле | Тип | Зміст |
|---|---|---|
| `НомерСчета` | Строка | Наш рахунок (IBAN або старий номер), для якого читається виписка |
| `Кодировка` | Строка | Кодування файлу; порожнє — читач визначає сам |
| `НачалоПериода` | Дата | Початок запитуваного періоду (для API) |
| `КонецПериода` | Дата | Кінець запитуваного періоду (для API) |
| `УчетныеДанные` | Неопределено | Облікові дані конектора; склад визначається разом із конекторами API, для файлових читачів порожнє |

## Конверт

| Поле | Тип | Хто заповнює | Зміст |
|---|---|---|---|
| `ВерсияКонтракта` | Число | платформа | Версія контракту; читач її **не змінює** |
| `НачалоПериода` | Дата | читач | Початок періоду виписки |
| `КонецПериода` | Дата | читач | Кінець періоду виписки |
| `НачальныйОстаток` | Число або `Неопределено` | читач, якщо `ДаетОстатки` | Залишок на початок; знак не обмежено |
| `КонечныйОстаток` | Число або `Неопределено` | читач, якщо `ДаетОстатки` | Залишок на кінець; знак не обмежено |
| `ЧтениеПолное` | Булево | читач | Див. нижче |
| `ГраницаДоверия` | Дата | читач | Для API — момент, до якого дані остаточні; для файлів порожня |
| `Диагностика` | ТаблицаЗначений | читач і платформа | Повідомлення про проблеми |
| `Операции` | ТаблицаЗначений | читач | Операції виписки |

Залишки необов'язкові. Знак не обмежено навмисно: овердрафт дає від'ємний залишок. Платформа
залишків не перевіряє.

### `ЧтениеПолное` — обов'язок читача

Початкове значення — `Ложь`. Читач ставить `Истина` **тільки** тоді, коли прочитав джерело
повністю й нічого не втратив. Початкове `Ложь` потрібне, щоб читач, який упав посередині,
не виглядав повним: від цієї ознаки залежить, чи може платформа посунути курсор регламенту
(дату, до якої все завантажено) через прочитаний період. Курсор не повинен перестрибнути
втрачені операції.

Той самий наслідок має відхилений платформою конверт: його читання **ніколи не вважається
повним для курсора**, хоч би яке значення поставив читач (див. «Що платформа робить з
конвертом»).

### `Диагностика`

Колонки:

| Колонка | Тип | Зміст |
|---|---|---|
| `Уровень` | Строка | Рівно `"Ошибка"` або `"Предупреждение"` (з урахуванням регістру); інше значення платформа вважає помилкою читача |
| `ПорядковыйНомер` | Число | Позиція в джерелі, до якої стосується повідомлення; `0` — до всієї виписки |
| `Текст` | Строка | Текст для адміністратора |

Читач записує сюди те, що помітив сам. Рівень `"Ошибка"` означає втрату даних: платформа
вважає таке читання таким, що має невалідні рядки (див. нижче). `"Предупреждение"` — інформація,
що даних не втрачає.

### `Операции`

Таблиця значень з такими колонками. Усі рядкові колонки — **без обмеження довжини**: типізована
рядкова колонка з довжиною мовчки обрізала б значення, а платформа хоче бачити справжнє й
повідомити про проблему.

| Колонка | Тип | Зміст |
|---|---|---|
| `ПорядковыйНомер` | Число (10 знаків, невід'ємне) | Позиція операції в джерелі, для діагностики й протоколу. `0` — не помилка: платформа підставить номер рядка таблиці, рахуючи з одиниці. Від'ємне значення колонка (кваліфікатор «невід'ємне») сама перетворює на `0`, тож далі діє те саме правило |
| `НомерСчета` | Строка | Наш рахунок, за яким прочитано операцію (IBAN або старий номер). Обов'язковий |
| `Валюта` | Строка | Числовий код ISO 4217 з трьох цифр, наприклад `"980"`; порожній — валюта рахунку |
| `ДатаОперации` | Дата і час | Дата й час операції. Порожня дата робить рядок невалідним |
| `НомерДокумента` | Строка | Номер платіжного документа у виписці |
| `ДатаДокумента` | Дата (лише день) | Дата платіжного документа, без часу |
| `Сумма` | Число (15,2) | Сума операції **строго більша за нуль**. Колонка має два знаки дробової частини: значення з більшою точністю округлюється до двох знаків під час присвоєння, до перевірки |
| `Направление` | Строка | Рівно `"Поступило"` або `"Списано"` |
| `ИдентификаторОперации` | Строка | Ідентифікатор операції в банку, якщо банк його дає; не довше 50 символів |
| `КонтрагентНаименование` | Строка | Назва контрагента |
| `КонтрагентНомерСчета` | Строка | Рахунок контрагента |
| `КонтрагентКод` | Строка | Код контрагента (ЄДРПОУ або ІПН) |
| `КонтрагентМФО` | Строка | МФО банку контрагента |
| `НазначениеПлатежа` | Строка | Призначення платежу, як у виписці |
| `СырыеДанные` | Строка | Вихідні дані операції як у джерелі, для розбору спірних випадків |

Контрагент, код, МФО, призначення, номер і дата документа можуть бути порожніми: комісія банку
не має контрагента, але лишається документом.

**У рядкові колонки читач кладе рядки.** Число, присвоєне рядковій колонці (`КонтрагентКод`,
`КонтрагентМФО`, `ИдентификаторОперации`), платформа перетворює на рядок із розділювачами груп,
а провідні нулі коду (ЄДРПОУ) втрачаються. Межа цього не бачить і не відхиляє, тож читач
сам передає код і ідентифікатор рядком, як у джерелі.

**Споживач конверта перевіряє порожність рядків через `ПустаяСтрока`**, не порівнянням з `""`:
`Валюта` і `НомерСчета` з самих пробілів контракт вважає порожніми, а порівняння з `""` такий
рядок пропустить.

#### Чому саме такі типи

Три вибори типів не очевидні, і кожен має причину.

**`Сумма` — число зі знаком «будь-який», а не «невід'ємне».** Типізована колонка з невід'ємним
знаком мовчки перетворила б від'ємне значення, яке читач розібрав помилково, на нуль, а нульовий
документ сховав би дефект читача. Тому знак не обмежено: від'ємна або нульова сума доходить до
перевірки з її справжнім значенням, **платформа відкидає такий рядок із діагностикою** (текст
повідомлення називає саме це значення), а не перетворює на нуль і не бере модуль. Напрямок руху
грошей передається колонкою `Направление`, а не знаком суми, тож сума завжди додатна.

**`ДатаОперации` — дата з часом, `ДатаДокумента` — лише день.** Час операції корисний читачам API
і для впорядкування, а ключ впізнавання вже завантаженої операції бере тільки день документа.
Типізована колонка мовчки перетворює нерозібране значення на порожню дату, тому порожня
`ДатаОперации` — прямий критерій невалідності, а не неявне «початок часів».

**Залишки — число або `Неопределено`, без обмеження знака.** Залишок необов'язковий (читач без
`ДаетОстатки` його не заповнює), а овердрафт дає від'ємні значення.

### Літерали контракту

Читач не знає модулів розширення, тому літерали пишуться в його коді буквально:

- напрям: `"Поступило"` (надходження) і `"Списано"` (списання);
- рівень діагностики: `"Ошибка"` і `"Предупреждение"`;
- валюта: три цифри числового коду ISO 4217 у рядку, `"980"` для гривні. Буквений код (`UAH`)
  читач перетворює сам;
- межа довжини `ИдентификаторОперации` — 50 символів: стільки вміщує сховище ідентифікатора
  транзакції банку. Довший ідентифікатор — помилка на межі, а не тихе обрізання.

## Що платформа робить з конвертом

Перевірка відбувається на межі, одразу після повернення з `Прочитать`. Платформа **нічого не
виправляє**: не обрізає ідентифікатор, не бере модуль суми, не підставляє дату. Вона лише
приймає чи відкидає.

### Відхиляється весь конверт

Якщо читач:

- підмінив `Выписку` — повернув або присвоїв параметру інший об'єкт, навіть побудований тим
  самим конструктором;
- змінив `ВерсияКонтракта`;
- зробив `Операции` або `Диагностика` чимось, що не є таблицею значень;
- змінив схему колонок цих таблиць: вилучив колонку, додав зайву або змінив тип чи його
  уточнення (довжину, розрядність, знак, склад дати).

Набір колонок порівнюється **за іменами й типами**; порядок колонок значення не має, бо читач
звертається до колонок за іменем.

Наслідки відмови: жоден рядок не завантажується, у діагностику записується повідомлення рівня
`"Ошибка"` про кожну причину, а читання **ніколи не вважається повним для курсора**. Діагностику
читача платформа зберігає, лише якщо конверт не підмінено й схема його таблиці діагностики
збігається з контрактом; у підміненому об'єкті таблиця діагностики чужа, і платформа в неї не
заглядає.

### Відкидається окремий рядок операції

Решта конверта завантажується, а відкинутий рядок отримує повідомлення `"Ошибка"` з номером
операції. Рядок відкидається, якщо:

| Правило | Умова невалідності |
|---|---|
| Дата операції | `ДатаОперации` порожня |
| Сума | `Сумма` менша або дорівнює нулю |
| Напрям | `Направление` не `"Поступило"` і не `"Списано"` |
| Валюта | `Валюта` не порожня й не рівно три цифри |
| Рахунок | `НомерСчета` порожній |
| Ідентифікатор | `ИдентификаторОперации` довший за 50 символів |

Один рядок може порушувати кілька правил — тоді кожне порушення дає окреме повідомлення.
Порожність решти колонок рядок не відкидає. Порожнім вважається і рядок із самих пробілів
(для `Валюта` і `НомерСчета`).

Нульова сума — найчастіший слід нерозібраного читачем значення, тому повідомлення про неї
додатково підказує цю причину.

### Рівень повідомлень читача

| Правило | Умова | Наслідок |
|---|---|---|
| Рівень діагностики | `Уровень` повідомлення читача не дорівнює **точно** `"Ошибка"` чи `"Предупреждение"` (зокрема `"ошибка"`, `"Error"`, порожній) | платформа додає власне повідомлення `"Ошибка"` з отриманим рівнем і номером рядка; ознака невалідних рядків стає `Истина` |

Платформа не трактує невідомий рівень як «усе, крім попередження»: помилка читача має бути
видимою, а не тихо перетлумаченою. Саме повідомлення читача лишається в діагностиці без змін.

### Ознака для курсора

Результат перевірки несе ознаку невалідних рядків. Вона стає `Истина`, якщо відкинуто хоч один
рядок, якщо сам читач записав повідомлення `"Ошибка"`, якщо рівень повідомлення читача не з
контракту **або якщо відхилено весь конверт**. У
регламенті конверт з такою ознакою вважається неповним: курсор не переходить дату відкинутої
операції, доки людина не розбереться.

## Версіонування

Поточна версія контракту — 1. Сумісність між версіями підтримується **лише додаванням колонок**.
Будь-яка інша зміна — зміна типу чи уточнення колонки, її вилучення, зміна літералу чи правила —
це нова `ВерсияКонтракта`. Платформа заявляє перелік версій, які вона приймає; читач із
версією поза переліком не підключається, адміністратор бачить повідомлення з назвою поля, версією
читача й переліком підтримуваних.

Читач не будує таблиць сам, а заповнює конверт платформи, тож нова колонка не ламає читача, який
про неї не знає: вона просто лишається порожньою.

## Підключення зовнішньої обробки

Зовнішня обробка-читач підключається так само, як нинішні обробки читання форматів:

1. Адміністратор реєструє обробку в довіднику БСП «Додаткові звіти та обробки»
   (`ДополнительныеОтчетыИОбработки`).
2. Обробка прив'язується до облікового запису банку реквізитом цього облікового запису.
3. Платформа створює обробку **без безпечного режиму**: у безпечному режимі заборонена робота з
   файлами, а читачам DBF і XML потрібен тимчасовий файл.
4. Відповідальність за вміст обробки лежить на адміністраторі, який її зареєстрував: вона
   виконується з повними правами.

Обробка мусить реалізувати `ОписаниеЧитателя` і `Прочитать`. Якщо опису немає або версія
контракту не підтримується, адміністратор отримує зрозуміле повідомлення.

Підключення — окремий етап платформи, а не частина межі конверта: повідомлення про відсутню
функцію читача і створення обробки без безпечного режиму є **обов'язком етапу підключення**.
Тут вони описані як вимога до нього; межа конверта (`ПроверитьВыписку`) їх не виконує.

## Чого контракт навмисно не включає

- **XDTO.** Пакет XDTO мусив би лежати в метаданих кожного розширення, а це складно для
  сторонніх розробників.
- **JSON.** Подвійна серіалізація, і в ньому немає типу «дата».
- **Типи конфігурації.** Посилання на довідники, документи чи перелічення в конверті зробили б
  читач залежним від конкретної конфігурації. Тому конверт описує лише факти банку, а
  розпізнавання контрагентів і видів операцій лишається платформі.
- **Ключ дедуплікації.** Його рахує платформа, а не читач; читач лише віддає
  `ИдентификаторОперации`, якщо банк його дає.
