# monobank: які є API і яке з них наше

Станом на 2026-09-14. Причина появи документа: у monobank **п'ять різних API**, вони
несумісні між собою, і з назв неочевидно, кому яке належить. Ми двічі втратили час,
розбираючись, чому виписка не містить призначення платежу — відповідь виявилась не в
нашому коді, а у виборі API.

Джерело відомостей — офіційні специфікації monobank, закріплене повідомлення офіційної
телеграм-групи «Monobank API» і обговорення в ній (експорт чату за 2026-07-30 … 2026-09-14),
а також [community-документація](https://github.com/andrew-demb/monobank-api-community-docs).
Робочі копії специфікацій лежали в `temp/` (гітігнорована) — у git їх не тримаємо, бо це
чужа документація, яка до того ж змінюється без попередження.

## П'ять API

| # | API | Хост | Чиї рахунки | Як отримати доступ |
|---|---|---|---|---|
| 1 | Відкрите персональне | `api.monobank.ua/personal/*` | **свої** — особисті, **ФОП**, банки | токен у кабінеті `api.monobank.ua`, read-only |
| 2 | Для провайдерів послуг | `api.monobank.ua` + `X-Sign` | **клієнтів** — особисті, ФОП | заявка на розгляд, read-only |
| 3 | **Рахунків юридичних осіб** | `corp-api.monobank.ua/ext/v1/*` | **своєї компанії (ТОВ)** | токен у кабінеті компанії `web.monobank.ua` |
| 4 | Open Banking | `ob.mono.bank` | клієнтів за consent | ліцензія НБУ (AISP/PISP) |
| 5 | Еквайринг (+ «Покупка частинами») | `monobank.ua/api-docs/acquiring` | мерчант-рахунок | окремий контур, не про виписки |

Дослівно із закріпленого повідомлення групи:

> API для персонального використання - свої рахунки (особисті, ФОП, банки)
> API для провайдерів послуг - рахунки клієнтів (особисті, ФОП)

Документація: [персональне](https://api.monobank.ua/docs/) ·
[провайдерів](https://api.monobank.ua/docs/corporate.html) ·
[юросіб](https://corp-api.monobank.ua/) · [Open Banking](https://ob.mono.bank/) ·
[еквайринг](https://monobank.ua/api-docs/acquiring)

## Головне: ФОП і ТОВ — це різні API

**ФОП не має доступу до API юридичних осіб.** Це не налаштування й не заявка — такої
можливості немає. Цитати учасників групи (2026-08-12 … 2026-08-23):

> «Тільки для тов є підготовка платежу на оплату. Всі інші рід-онлі»
> «Виключно в ТОВ є така можливість»
> «Ну фоп це вроді не тов і значення слів "тільки для тов" тоже не помінялося»

Пропозиція «а ФОП щоб зробили токени як для ТОВ» звучить у групі як побажання до банку,
тобто функції немає. Виписки ФОП живуть там само, де виписки фізосіб — у персональному API.

Наслідок для підсистеми: **обидва режими потрібні постійно**, а не тимчасово задля
сумісності. Продукт має підтримувати персональне API (ФОП) і API юросіб (ТОВ) паралельно.

| Клієнт | Яке API | Виписка | Призначення платежу | Платіжки з 1С |
|---|---|---|---|---|
| **ФОП** | персональне (#1) | так | **ні** — лише опис/коментар | ні |
| **ТОВ** | юросіб (#3) | так | так | готує платіжку, підписує людина в застосунку |

## Чому issue #10 нерозв'язний для ФОП

[Issue #10](https://github.com/VSydorenko/SMP_BankExchange/issues/10) — «замість призначення
платежу використовується коментар». Причина не в нашому коді.

У monobank **немає окремого поля «призначення платежу»** в персональному API — звірено по
трьох специфікаціях (персональна, провайдерська, community-копія): набір полів `StatementItem`
в усіх трьох ідентичний. Є лише два текстові поля:

| Поле | Персональне API (#1) | API юросіб (#3) |
|---|---|---|
| `description` | «Опис транзакцій» | **«Призначення операції»** |
| `comment` | «Коментар до переказу, уведений користувачем. Якщо не вказаний, поле буде відсутнім» | поля немає |

Те, що призначення платежу через персональне API недоступне, підтверджують і в групі:
побажання «я б іще призначення платежу показував для переказів по айбану, хоча б для
вихідних» (2026-08-09) і згадка про роботу з ФОП-виписками як про «зчитування і парсинг
**коментаря** до платежу». Окремо зазначено, що додані вручну коментарі, теги й файли в API
не потрапляють узагалі.

Провайдерське API (#2) тут не рятує — схема транзакції в ньому та сама.

**Висновок:** для ФОП максимум можливого — склеювати `description` + `comment`, щоб не
втрачати те, що банк усе-таки віддає. Повне призначення платежу для ФОП недоступне за
рішенням банку. Для ТОВ через API юросіб воно є.

## Чим API юросіб відрізняється технічно

Важливо для тих, хто писатиме інтеграцію — відмінності не косметичні:

| | Персональне (#1) | Юросіб (#3) |
|---|---|---|
| Ідентифікатор рахунку | внутрішній `id`, спершу треба `client-info` | **IBAN напряму** |
| Заголовки | `X-Token` | `x-token` + **обов'язковий** `accept: application/json` |
| Ліміт частоти | «не частіше ніж 1 раз у 60 секунд» | ліміт на компанію; залишок у заголовку `x-rate-limit-remaining`, пауза в `x-rate-Limit-retry-after-seconds` |
| Обмеження періоду | «31 доба + 1 година (2682000 секунд)» | у специфікації не описане |
| Розмір сторінки | до 500, параметра немає | параметр `limit`, максимум 500, **за замовчуванням 10** |
| Статус операції | `hold` (булеве) | `status`: `DONE` / `PENDING` / `DECLINED` |
| Час | `time` | `time` (створення) + `completedTime` (проведення) |
| Код валюти | число `980` | **рядок** `'980'`; при цьому в `Account.currency` — число |
| Суми | копійки | копійки, але `Account.balance` — **в одиницях валюти** |
| Контрагент | `counterIban`/`counterEdrpou` «лише для рахунків ФОП» | завжди, плюс `ultimateDebit` (фактичний платник) |
| Ідентифікатор транзакції | рядок на кшталт `ZuHWzqkKGVo=` | **UUID** (36 символів) |
| Вебхук | є | **немає** |

Три пастки, на яких легко втратити дані:

1. **`limit` за замовчуванням 10.** Не передали параметр — отримали десять операцій замість
   виписки. У поєднанні з механізмом «документів, яких немає у виписці, позначати на
   видалення» це не просто неповнота, а втрата вже завантажених документів.
2. **Одиниці різні всередині одного API** — транзакції в копійках, баланс рахунку в гривнях.
3. **UUID не влазить у наявний регістр.** `РегистрыСведений.СМП_НомерПоследнейТранзакции`,
   ресурс `ИДТранзакции` — рядок довжиною 20; UUID потребує 36.

Пагінації з offset немає в жодному з API: коли повернулося рівно `limit` записів, наступний
запит роблять зі зменшеним `to` — до часу останньої отриманої транзакції, доки не прийде
менше за ліміт.

## Чого не варто планувати

**Open Banking (#4) — не наш випадок.** Це контур для фінансових установ із ліцензією НБУ;
доступ керується регулятором. За свідченнями учасників групи, які проходили цей шлях,
отримання ліцензії AISP — «десятки тисяч доларів», лише розгляд заявки коштує близько
6 тис. доларів, а строк — від пів року. Вендор облікового ПЗ туди не йде.

**Sandbox для API юросіб не існує.** На пряме питання представник банку відповів: «Ні, немає
такого. Тільки `corp-api.monobank.ua`». Тестувати доведеться на живому рахунку ТОВ.

**Платежі з 1С не будуть повністю автоматичними.** `/ext/v1/payment/prepare` готує платіжку,
але «платіжки в роботу підуть тільки коли власник в додатку їх підтвердить».

## Дрібниця, яка коштувала нам помилки

Закріплене повідомлення групи прямо попереджає:

> Звертайте увагу що дати в Unix Time Stamp - тобто як UTC (+0:00), а в нас час +2:00/+3:00

Саме цього не враховує `СМП_РаботаСБанкамиМонобанкAPIСервер.ДатаВремяВUnixTime` — межі
періоду зсунуті на величину часового поясу.
